## 1대분류. 물리 센서 데이터 수집 계층 (Physical Capture Tier)

#### 🎯 Step 1-3: 오디오 하드웨어 클럭(I2S Clock) 및 APLL 정합성 검증
오디오(ICS43434 마이크 등)의 42kHz 정밀 샘플링을 보장하기 위한 I2S 하드웨어 드라이버 설정과 DMA 버퍼 정합성을 라인 단위로 전수 검사했습니다.
 * **번호:** 8
 * **모듈:** T210_Def / T230_Sensor
 * **문제점:** 소음 파이프라인의 격리와 샘플링 지터(Jitter) 최소화를 위해 T210_Def.hpp에 고정밀 오디오 전용 아날로그 PLL 제어 상수인 USE_APLL_DEF = true가 강력히 규정되어 있습니다. 그러나 T230_Sensor_248.cpp에서 실제 I2S 하드웨어를 기동하는 i2s_config_t 구조체를 세팅할 때, .use_apll 멤버에 이 상수를 매핑하는 코드가 누락되었거나 타 도메인의 변수가 오인 대입되어 있습니다. 이로 인해 기본 클럭이 사용되어 고음역대 주파수 분석 시 스펙트럼이 미세하게 틀어지는 물리적 왜곡이 발생합니다.
 * **개선방향:** CL_T2_SensorEngine::init() 내의 I2S 드라이버 초기화 블록에서 .use_apll = T2_Def::Audio::Hardware::USE_APLL_DEF;로 1:1 명시적 바인딩을 적용하여 정밀 클럭을 강제 가동할 것.
 * **번호:** 9 (신규 확인 이슈)
 * **모듈:** T210_Def / T230_Sensor
 * **문제점:** T210_Def.hpp에는 오디오 프레임 처리를 위해 FFT_SIZE_MAX (예: 1024)가 정의되어 있고, 상위 FSM은 24.38ms 단위로 이 크기만큼 데이터가 준비되기를 기대합니다. 그러나 T230_Sensor_248.cpp 내부의 I2S DMA 버퍼 설정(.dma_buf_len 및 .dma_buf_count)이 이 상수와 연동되지 않고 하드코딩되어 있습니다. DMA 하드웨어 인터럽트 주기와 소프트웨어의 특징 추출 요구 주기가 어긋나면서, 미세한 I2S 언더런(Underrun)이나 CPU 대기 지연(Blocking)이 발생합니다.
 * **개선방향:** i2s_config_t 설정 시 .dma_buf_len = T2_Def::Audio::Sensor::FFT_SIZE_MAX;로 동적 할당하고, .dma_buf_count를 최소 4~6 이상으로 설정하여 FSM 루프 주기와 DMA 하드웨어 버스트 주기를 완벽히 일치시킬 것.
 * **번호:** 10 (신규 확인 이슈)
 * **모듈:** T230_Sensor / T245_FeatExtra
 * **문제점:** I2S 마이크(ICS43434 등)는 물리적으로 24-bit 데이터를 전송하고, ESP32의 I2S 드라이버는 이를 32-bit 공간에 패딩하여 수신합니다. T230_Sensor_248.cpp에서 i2s_read로 바이트를 읽어 float 배열로 변환하여 DSP 엔진으로 넘기는 과정에서, 24-bit 부호 확장(Sign Extension)을 위한 비트 시프트 마스킹((int32_t)(raw_val << 8) >> 8) 처리가 누락되어 있습니다. 이 상태로 정수-실수 변환을 수행하면 음수 파형 진폭이 완전히 깨지거나 심각한 DC 오프셋이 발생하여 노이즈 지표 전체가 붕괴됩니다.
 * **개선방향:** I2S 버퍼에서 데이터를 인출하여 float 파형 슬롯에 적재하는 루틴(accumulateAudio 등) 내부에 명시적인 24-bit to 32-bit 부호 확장 비트 연산을 추가한 뒤 (float) 캐스팅을 수행할 것.

## 1대분류. 물리 센서 데이터 수집 계층 (Physical Capture Tier)
### 2단계: 멀티코어 비동기 링버퍼 및 원자성(Atomicity) 검증
#### 🎯 Step 2-1: 멀티코어 간 공유 변수 레이스 컨디션(Race Condition) 정밀 조사
Core 0(인터럽트 및 데이터 수집)과 Core 1(신호 처리 및 FSM) 사이에서 데이터를 교환할 때, 락(Lock) 없이 접근하여 데이터가 찢어지거나 오염되는 변수가 있는지 링버퍼 생명주기를 전수 추적했습니다.
 * **번호:** 11 (기존 #1 연계 및 심화)
 * **모듈:** T230_Sensor / T290_FsmMgr
 * **문제점:** Core 0의 _imuAcqTask가 호출하는 accumulateFifo() 내부에서 링버퍼 쓰기 포인터(_accumWriteIdx)와 누적 카운트(_accumCount, _accumGCount)를 증가시킵니다. 동시에 Core 1의 _vibProcessTask는 getAccumulatedAccel() 등을 호출하여 같은 카운트 변수를 감소(_accumCount--)시킵니다. 현재 센서 엔진에 존재하는 _spiLock은 SPI 통신 선로 점유만 막아줄 뿐, 이 메모리 변수들에 대한 보호 장치가 전혀 아니므로 멀티코어 간 원자성(Atomicity)이 깨져 센서 데이터 인덱스가 완전히 꼬이게 됩니다.
 * **개선방향:** 링버퍼 인덱스 증감 및 데이터 복사가 일어나는 변수 연산 구역 전후에 FreeRTOS 인터럽트 안전 임계 영역(taskENTER_CRITICAL(), taskEXIT_CRITICAL())을 선언하거나, 링버퍼 전용 경량 스핀락(Spinlock)을 추가 구현하여 물리적 동시 접근을 원천 차단할 것.
 * **번호:** 12 (신규 확인 이슈)
 * **모듈:** T230_Sensor / T290_FsmMgr

 * **모듈:** T220_CfgMgr / T240_DspEng / T290_FsmMgr
 * **문제점:** 사용자가 튜닝을 적용하면 Web 서버 태스크(비동기)에서 CfgMgr를 거쳐 CL_T2_DspEngine::reloadFilters()를 호출하여 필터 계수 배열(notch_coeffs, iir_coeffs 등)을 덮어씁니다. 이때 Core 1에서는 _audioProcessTask가 processAudio()를 통해 해당 계수를 읽으며 고속 SIMD 연산을 수행 중일 수 있습니다. **DSP 엔진 내부에 읽기/쓰기 락(Mutex)이 전혀 없기 때문에**, SIMD 벡터 루프가 도는 도중 계수 절반이 새 값으로 바뀌어버리는 현상이 발생하며, 이는 즉각적인 NaN 발산 및 커널 FPU 패닉(Core Dump)을 유발합니다.
 * **개선방향:** CL_T2_DspEngine 내부에 필터 계수 적용 전용 경량 Mutex(_dspLock)를 신설하고, reloadFilters()에 의한 계수 덮어쓰기와 process*() 계열 함수의 고속 연산이 절대로 동시에 실행되지 않도록 상호 배제(Mutual Exclusion)를 철저히 구현할 것.
 * **번호:** 33 (추가 발굴 이슈)
 * **모듈:** T240_DspEng
 * **문제점:** 오디오 FIR 필터에 사용되는 dsps_fir_f32_t 제어 구조체는 초기화 시 필터 탭(Taps) 수와 연산 프레임 길이에 맞는 전용 상태 버퍼(State Array)를 필요로 합니다. 런타임에 캘리브레이터나 설정 갱신을 통해 FIR 계수 탭수가 가변(예: 63 -> 127)될 수 있는데, reloadFilters()에서 계수 값(fir_coeffs)만 복사할 뿐, **ESP-DSP 라이브러리의 dsps_fir_init_f32()를 다시 호출하여 상태 포인터와 딜레이 라인 사이즈를 재구성하는 로직이 누락**되어 있습니다. 이로 인해 변경된 탭수가 기존 할당된 메모리 경계를 침범하여 힙 오버플로우(Heap Overflow)가 발생합니다.
 * **개선방향:** FIR 필터 계수의 길이(Taps)나 내용이 핫스왑될 경우, 반드시 dsps_fir_init_f32()를 재호출하여 내부 State 버퍼의 인덱스를 안전하게 초기화하고 바인딩을 갱신하는 셋업 코드를 연쇄시킬 것.
 * **번호:** 34 (추가 발굴 이슈)
 * **모듈:** T240_DspEng / T290_FsmMgr
 * **문제점:** 장비 구동 중 자원 절약을 위해 특정 축이나 마이크 채널을 비활성화(axis_mask, channel_mask Off)해 두었다가, 런타임 튜닝으로 다시 켜는(On) 상황입니다. DSP 엔진은 비활성 채널의 연산을 건너뛰기 때문에 해당 채널의 히스토리 버퍼(median_hist, prev_pre_emp 등)에는 수 시간 전 비활성화될 당시의 과거 데이터가 고스란히 남아있습니다. 이를 **아무런 초기화 없이 핫스왑 즉시 연산에 재투입하면, 과거와 현재 파형의 단차가 극심하게 발생하여 거대한 임펄스(가짜 충격 파형)가 생성되고 즉각 RULE_NG 오탐지 경보**가 울립니다.
 * **개선방향:** FSM 매니저 또는 DSP 엔진 상단에 이전 프레임의 mask 상태와 현재 프레임의 mask 상태를 비트 단위로 비교(XOR 연산 등)하는 가드를 두고, **새롭게 켜진(Wake-up) 채널이 감지되면 해당 채널 전용의 DSP 상태 변수들만 선별적으로 제로 클리어(memset)**하는 '웜 부트(Warm-boot) 초기화' 로직을 추가할 것.

### 4단계: 분석 창 함수(Windowing) 및 디지털 필터 계수 정합성 검증
#### 🎯 Step 4-2: 도메인별 FIR 필터 탭수(Taps) 제한 및 상태 버퍼 크기 일치 여부 정밀 추적
ESP-DSP 라이브러리의 FIR 필터(dsps_fir_f32_t)가 요구하는 엄격한 메모리 할당 공식과 SIMD(싱글 인스트럭션 멀티플 데이터) 가속 조건이 실제 런타임 버퍼 구조체와 일치하는지 라인 단위로 대조했습니다.

 * **문제점:** ESP-DSP 라이브러리의 FIR 연산 함수를 구동하려면, 딜레이 라인을 저장하는 상태 버퍼(State Buffer)의 크기가 반드시 (필터 탭수 + 1회 처리할 프레임 샘플 수) 이상이어야 합니다. 그러나 T240_DspEng_248.hpp 내의 DSP 런타임 구조체(ST_AudioDspRuntime 등)를 보면, FIR 필터의 상태 배열 크기가 이 합산 규격(FIR_TAPS_MAX + FFT_SIZE_MAX)을 온전히 수용할 만큼 명확한 수식으로 할당되어 있지 않습니다. 이 상태에서 최대 탭수와 최대 블록 크기로 processAudio가 구동되면 배열 끝단을 넘어가는 힙 메모리 오버플로우(OOB Write)가 즉각 발생합니다.
 * **개선방향:** T240_DspEng_248.hpp 내부의 FIR 상태 배열 선언부를 alignas(16) float fir_state[2][T2_Def::Audio::Sensor::FFT_SIZE_MAX + T2_Def::Audio::FeatureLimit::FIR_TAPS_MAX];와 같이 탭수와 블록 크기를 합산한 명시적 컴파일 상수로 재정의하여 메모리 경계를 보호할 것.

 * **개선방향:** 델타 차분 수식 수행 직후, 계산된 d_rms 및 dd_rms 절대값이 부동소수점 안전 하한선(예: 1e-7f) 미만일 경우 하드웨어 연산 장치에 부담을 주지 않도록 강제로 명시적 0.0f를 대입하는 클리핑 가드를 적용할 것.

## 2대분류. 신호 처리 및 특징 추출 계층 (DSP & Feature Tier)
### 6단계: 소음 도메인(Audio/MFCC) 특징량 연산 누락 검증
#### 🎯 Step 6-2: 정밀 사운드 진단용 켑스트럼 오차 허용치 및 피크 노이즈 마진 가드 로직 추가 정밀 재점검
켑스트럼 분석 파이프라인에서 발생할 수 있는 복잡한 예외 상태를 추적했습니다. 단순 연산 모순을 넘어 **동적 메모리 경계 침범, 켑스트럼 리프팅(Lifting) 창 함수의 차수 불일치, 그리고 고주파 진폭 대칭성 붕괴로 인한 메모리 오염 틈새 3건**을 추가 적발했습니다.
 * **번호:** 73 (추가 발굴 이슈)
 * **모듈:** T245_FeatExtra
 * **문제점:** 켑스트럼 연산을 위해 실수 로그 스펙트럼 배열을 역 FFT(IFFT)로 밀어 넣을 때, ESP-DSP 라이브러리의 dsps_fft_f32 또는 전용 IFFT 함수는 입력 데이터의 길이가 반드시 2의 거듭제곱(2^n) 형태인 복소수 배열 구조를 유지해야 합니다. 그러나 오디오 특징량 추출부에서 오디오 멜-필터뱅크(Mel-Filterbank)를 거친 후의 중간 해상도 배열 크기(예: 40 또는 80개 빈)를 그대로 켑스트럼 연산용 복소수 입력 버퍼에 밀어 넣고 있습니다. 이 채우기(Padding) 오류로 인해 IFFT 연산 함수가 힙 메모리 할당 한계 경계를 넘어 주변 스레드의 컨텍스트 영역을 영구적으로 오염시키는 Out-of-Bounds Write 결함이 존재합니다.
 * **개선방향:** 켑스트럼 IFFT 구동 직전, 입력 버퍼의 크기를 강제로 다음 순위의 2의 거듭제곱 크기(예: 1024 또는 512)를 추종하는 고정 메모리 규격으로 격리하고, 유효 소음 데이터 이외의 잔여 배열 인덱스는 전체 0.0f로 제로 패딩(Zero Padding)하는 하드웨어 안전 가드를 구현할 것.
 * **번호:** 74 (추가 발굴 이슈)
 * **모듈:** T210_Def / T245_FeatExtra
 * **문제점:** 켑스트럼 영역에서 고주파 노이즈 성분을 억제하고 특정 고조파 피크(Quefrency Peak)의 가시성을 높이기 위해 T210_Def.hpp 스펙에 켑스트럼 리프팅 창 함수(Cepstral Liftering Window) 적용이 의도되어 있으나, 정작 T245_FeatExtra_248.cpp 내부에는 리프팅 가중치 계수 배열(_lifterCoeffs)을 생성하거나 켑스트럼 결과물에 일괄 곱해주는 창 함수 가속 필터가 유실되어 있습니다. 이로 인해 미세한 고주파 베어링 결함 음향 신호가 저주파 음성 배경 소음에 묻혀 상위 판정 레이어로 전달되지 못하는 기계적 징후 유실 틈새가 존재합니다.
 * **개선방향:** CL_T2_FeatureExtractor 생성자 단에 지정된 차수(MFCC_DIM_DEF)를 기반으로 가중치를 생성하는 for (int i=0; i<dim; i++) _lifterCoeffs[i] = 1.0f + (dim/2.0f) * sinf(PI * i / dim); 공식의 리프팅 필터 테이블을 빌드하고, 켑스트럼 산출 직후 이를 고속 일괄 곱셈하도록 파이프라인을 복원할 것.
 * **번호:** 75 (추가 발굴 이슈)
 * **모듈:** T245_FeatExtra / T270_Commu
 * **문제점:** 켑스트럼 피크 및 평균 비율(cpsr_max, cpsr_mxr) 계산 완료 후, 추출된 최종 특징량 정보들이 직렬화 통신 채널(T270_Commu)로 브로드캐스트되는 과정에서의 데이터 찢어짐 예외입니다. 켑스트럼 분석은 고부하 연산이므로 오디오 프레임 주기(24.38ms) 내부에서 찰나의 연산 지연이 발생하면, 다음 소음 프레임의 I2S 수집 인터럽트와 동시성 충돌을 일으킵니다. 이때 켑스트럼 연산 출력 버퍼가 강제로 스와핑되는 과정에 가드가 없어, **전반부 퀴프런시 성분은 현재 프레임 데이터이고 후반부 성분은 다음 주기의 데이터로 급치환되는 페이로드 Tearing(찢어짐) 상태**로 통신 스트림 패킷이 불완전 조립됩니다.

### 7단계: 다중 주율(Multi-rate) 시점 불일치 및 텐서 조립 정합성 검증
#### 🎯 Step 7-1: 다중 주율 주기 비대칭에 따른 시점 모순 및 찢어짐(Tearing) 상태 점검
소음(24.38ms)과 진동(640ms)의 생산 주기 비대칭성이 SeqBuilder::pushVector 레이어에서 조립될 때 유발하는 시점 모순 상태를 라인 단위로 정밀 추적했습니다.

 * **번호:** 80 (신규 확인 이슈)
 * **모듈:** T248_SeqBuild
 * **문제점:** SeqBuilder 내부의 시계열 텐서 슬라이딩 윈도우 버퍼(_tensorWindowBuf) 구조에서 데이터 밀어내기(Push/Pop) 연산 시 원자성이 보장되지 않습니다. 24.38ms마다 고속으로 호출되는 pushVector()가 내부 링버퍼 인덱스를 조작하는 찰나에, FSM 매니저나 판정 엔진이 비동기적으로 getTensorPointer()를 호출하여 데이터를 참조해 가면, **버퍼 이동 연산 중간에 텐서 메모리를 복사해가게 되어 텐서의 일부 인덱스는 갱신 전 프레임, 일부 인덱스는 갱신 후 프레임 데이터가 혼재되는 페이로드 오염**이 유발됩니다.
 * **개선방향:** CL_T2_SeqBuilder 클래스 내부에 고속 텐서 가축 전용 경량 스핀락(_tensorSpinlock)을 신설하고, pushVector 메모리 시프트 구역과 외부 인출 구역 전체를 이 락으로 상호 배제 가드 조치할 것.
 * **번호:** 81 (신규 확인 이슈)
 * **모듈:** T215_Type / T248_SeqBuild
 * **문제점:** ST_Slot_Header_t 내부에 존재하는 데이터 손실/불연속성 알림 마커인 sequence_loss_flag 파라미터가 SeqBuilder 레이어에서 완전히 유시된 채 취급됩니다. 센서 드라이버나 I2S 하드웨어 결함으로 인해 데이터 시퀀스가 누설(Drop)되었음을 헤더 플래그가 명시하고 있음에도, SeqBuilder는 이를 무시하고 깨진 특징량을 슬라이딩 윈도우에 그대로 밀어 넣습니다. 이로 인해 한 번 발생한 불연속 가비지 데이터가 윈도우 버퍼 크기만큼(예: 10 프레임 동안) 버퍼 내에 잔류하면서 하위 추론 신경망에 지속적인 가짜 결함 오탐지 연쇄 반응을 일으킵니다.
 * **개선방향:** pushVector() 진입문 상단에 유입 데이터 헤더 검증식을 신설하여 if (p_header.sequence_loss_flag) 조건 만족 시 현재 윈도우 버퍼 전체를 즉각 제로 클리어(memset)하고 텐서 조립 웜업 카운터를 초기화하는 방어 코드를 인입할 것.

#### 🎯 Step 7-1: 다중 주율 주기 비대칭에 따른 시점 모순 및 찢어짐(Tearing) 상태 추가 정밀 재점검

 * **모듈:** T260_TensorEng
 * **문제점:** AI 모델의 학습 시점 규격에 맞춰 입력 특징량 벡터들을 0.0f \sim 1.0f 또는 -1.0f \sim 1.0f 공간으로 압축하는 정규화(Normalization) 엔진 내부에서, 가속도, 자이로, 오디오의 물리적 단위계 차이를 무시하고 단일 정적 스케일링 인자(GLOBAL_SCALE_FACTOR)로 전체 텐서 배열을 일괄 나눗셈 연산하는 치명적인 연산 왜곡이 존재합니다. 이로 인해 원시 값의 스케일이 상대적으로 작은 자이로(dps)나 오디오(MFCC) 지표들은 정규화 통과 후 가중치 연산에 영향을 주지 못하는 영(0)에 가까운 값으로 전사 소거되며, 오직 진폭이 큰 가속도 특징량만 모델 추론을 독점하는 논리적 모순이 발생합니다.

 * **개선방향:** 정규화 연산 구문 종단에 std::clamp(v_norm, 0.0f, 1.0f) (또는 모델 사양에 맞춰 -1.0f \sim 1.0f) 수식을 배치하여, 물리적 예외 입력이 주입되더라도 AI 입력 텐서 공간의 경계선 내부로 부동소수점 수렴성을 강제 제어하는 수치적 가드를 씌울 것.

### 8단계: TinyML 추론 엔진 입력 텐서 바인딩 및 런타임 수렴성 검증
#### 🎯 Step 8-3: 추론 결과 가중치(Softmax/Logits) 해석 오류 및 인터락 출력 누락 점검
TFLM 인터프리터의 추론 결과물인 출력 텐서(Output Tensor)의 배열 인덱스 해석과, 최종 판정 등급(정상/주의/결함)이 상위 상태 머신 및 외부 제어 장치로 유실 없이 전달되는지 파이프라인의 종단을 정밀 추적했습니다.
 * **번호:** 97 (기존 #14 이슈 연계 및 종단 확장)
 * **모듈:** T260_TensorEng / T290_FsmMgr
 * **문제점:** AI 모델의 출력 레이어가 Softmax인 경우 각 분류 클래스(예: [0]: 정상, [1]: 베어링 불량, [2]: 벨트 정렬 불량)의 확률값 합은 항상 1.0f (100\%)가 됩니다. 그러나 현장 튜닝 중 출력 레이어가 Softmax가 누락된 Raw Logits(실수 전체 범위) 형태로 빌드된 모델이 업로드될 경우, 추론 엔진 내 가드 로직은 이를 구분하지 않고 기존 Softmax용 고정 임계치 수식(if (p_out[i] > 0.85f))을 그대로 적용합니다. Logits 스케일에서는 정상 출력이 5.2f처럼 큰 값이 나올 수 있으므로, 임계치 비교문이 모든 클래스에 대해 상시 참(True)이 되어 FSM이 다중 결함 상태로 동시 천이하는 논리 붕괴가 발생합니다.
 * **개선방향:** CL_T2_TensorEngine 내부에 현재 로드된 모델의 출력 텐서 타입 플래그(_isLogitsOutput)를 추가하고, Logits 형태일 경우 출력 배열 전체를 지수 함수 공간으로 투영하여 확률 스케일로 정규화하는 Softmax 보정 래퍼 수식을 연쇄 인입할 것.
 * **번호:** 98 (신규 확인 이슈)
 * **모듈:** T260_TensorEng / T250_TriggerEng
 * **문제점:** AI 추론을 통해 특정 결함 클래스의 확률 가중치가 임계치를 초과(kTfLiteOk 후 판정 완료)했음에도 불구하고, 이 인공지능 기반 판정 출력이 룰베이스 판정 매니저인 CL_T2_TriggerEngine으로 라우팅되는 파이프라인이 단절되어 있습니다.  * **개선방향:** TensorEng 종단부에 추론 성공 엣지 콜백을 신설하고, 산출된 최상위 확률 클래스 인덱스와 가중치 정보를 TriggerEng::injectAiResult(uint8_t class_idx, float confidence) 인터페이스를 통해 실시간 주입하여 룰베이스와 AI 판정이 통합 의사결정을 내리도록 구조를 결합할 것.

 * **번호:** 106
 * **모듈:** T250_TriggerEng
 * **문제점:** 현재 TriggerEng 내부의 최종 상태 결정 블록이 독립적인 여러 개의 if문 구조로 수평 배치되어 있습니다. 진동 임계치 초과 시 _nextState = FAULT_VIB;를 수행한 직후, 소음 임계치 초과 조건문이 연쇄적으로 참이 되면 _nextState = FAULT_AUD;로 오버라이트(덮어쓰기) 됩니다. 만약 **물리적으로 훨씬 더 치명적인 기계적 파손(진동 폭발)이 일어났음에도 불구하고, 단순 소음 경고 수준의 신호가 마지막 if문에 배치되어 있다는 이유로 최상위 결함 상태가 마스킹(은폐)**되어 상위 FSM에 하위 등급의 경보가 전송되는 아키텍처 논리 모순이 존재합니다.
 * **개선방향:** 결함 상태의 강도와 위험도에 따라 명시적 가중치를 부여하는 우선순위 인코더(Priority Encoder) 제어 구조를 도입하고, if-else if 계층 가드를 설계하여 상위 위험 등급인 치명적 결함(CRITICAL_FAULT)이 감지되면 하위 경고 분기문들이 원천 마스킹(Bypass)되도록 보완할 것.
 * **번호:** 107 (신규 확인 이슈)
 * **모듈:** T250_TriggerEng / T290_FsmMgr
 * **문제점:** 설비가 심각한 결함 상태로 판단되어 FSM이 이미 EM_SystemState_t::FAULT 상태로 진입해 인터락 릴레이를 차단하고 있는 상황입니다. 이때 하위 TriggerEng 레이어는 래치 해제 버튼이 눌리기 전까지 연산을 멈추거나 출력을 동결해야 함에도, 백그라운드 태스크에서 센서 특징량을 기반으로 RULE_NG 여부를 계속 연산하여 FSM 매니저 큐에 상태 전이 명령을 중복 발송합니다. 이로 인해 **이미 FAULT 상태인 시스템에 "정상 복구 및 재진입" 관련 내부 메시지가 섞여 들어가 FSM 상태 전이 기계가 교란**되거나 예기치 못한 상태 롤백 현상이 유발됩니다.

 * **개선방향:** 다중 결함 플래그 주입 구문을 원자적 비트 OR 연산 구조(p_header.fault_flags |= EM_StatusBit_t::FAULT_ACC;)로 전면 리팩토링하여, 동시 다발적 결함 징후의 물리적 흔적이 유실 없이 페이로드 헤더에 완전하게 누적 보존되도록 조치할 것.

## 4대분류. 통신 및 페이로드 엔지니어링 계층 (Commu & Payload Tier)
### 10단계: 직렬화 페이로드 인코딩 및 메모리 정렬 무결성 검증
#### 🎯 Step 10-1: 구조체 바이트 패딩(#pragma pack) 불일치로 인한 이기종 기기 간 엔디안/메모리 찢어짐 점검
ESP32-S3(32비트 RISC-V/Xtensa 코어) 아키텍처 환경에서 조립된 특징량 구조체 바이너리가 네트워크 직렬화(T270_Commu)를 거쳐 x86/x64 기반 상위 진단 서버나 게이트웨이로 전송될 때, 컴파일러 고유의 바이트 정렬 규격 및 엔디안 비대칭성으로 인한 데이터 왜곡을 라인 단위로 추적했습니다.
 * **번호:** 109 (기존 #41 이슈 연계 및 통신단 심화)
 * **모듈:** T215_Type / T270_Commu
 * **문제점:** T215_Type.hpp 내부에 정의된 수십 개의 구조체(ST_Slot_Accel_t, ST_Slot_Audio_t 등) 선언부에 컴파일러 바이트 패딩 제어 지시어인 #pragma pack(push, 1) 또는 __attribute__((packed)) 가 누락되어 있습니다. 이로 인해 32비트 임베디드 컴파일러는 메모리 접근 효율을 위해 구조체 중간중간에 가짜 바이트(Padding Byte)를 임의로 인입합니다. 이 버퍼를 그대로 바이너리 덤프(memcpy)하여 상위 64비트 서버 플랫폼으로 전송하면, 양측의 메모리 오프셋 지도가 완전히 어긋나 고차 통계치와 주파수 밴드 에너지가 엉뚱한 바이트 덩어리와 섞여 찢어지는 메모리 정렬 붕괴 현상이 발생합니다.
 * **개선방향:** T215_Type.hpp 내의 모든 네트워크 통신 대상 구조체 정의 상하단에 #pragma pack(push, 1) 및 #pragma pack(pop)을 명시적으로 감싸 컴파일러 간의 바이트 얼라인먼트 규격을 1바이트 단위로 강제 통일할 것.
 * **번호:** 110 (신규 확인 이슈)
 * **모듈:** T270_Commu
 * **문제점:** ESP32-S3 하드웨어 아키텍처는 리틀 엔디안(Little-Endian) 방식을 사용하는 반면, 표준 네트워크 통신 프로토콜 페이로드는 빅 엔디안(Big-Endian, Network Byte Order) 규격을 준수해야 합니다. 현재 통신 모듈의 소켓 버퍼 주입 루틴을 보면, 멀티바이트 필드(예: uint32_t sequence_loss_flag, float centroid)들에 대해 htons() 또는 htonl() 계열의 엔디안 변환 처리가 완전히 유실된 채 생(Raw) 바이트로 스트리밍하고 있습니다. 이로 인해 빅 엔디안 가이드를 따르는 수신측 시스템이 최상위/최하위 바이트 위치를 거꾸로 파싱하여 정상 데이터가 수억 배 부풀려진 기형적 수치로 왜곡됩니다.
 * **개선방향:** 바이트 패킹 직후 페이로드 헤더 및 정수형 데이터 필드에 대해 htonl() 복사 스왑 필터를 바인딩하고, 부동소수점(float) 데이터의 경우 IEEE 754 포맷의 바이트 시퀀스를 안전하게 역전시키는 전용 마이크로 스왑 매크로 함수(swapFloat())를 통신 레이어 종단에 주입할 것.
 * **번호:** 111 (신규 확인 이슈)
 * **모듈:** T215_Type / T270_Commu
 * **문제점:** 구조체 바이너리를 바이트 포인터(uint8_t*)로 강제 캐스팅하여 raw 소켓이나 MQTT 페이로드로 밀어 넣을 때 발생하는 전산학적 언더플로우 경계 예외입니다. 구조체의 총 바이트 크기인 sizeof(ST_Master_Packet_t) 연산 결과가 하드웨어 소켓 MTU(Maximum Transmission Unit, 통상 1500바이트) 한계선을 미세하게 초과하는 가변 패킷 확장 설계 오류가 존재합니다. 패킷 크기가 MTU 경계를 넘어서는 순간 IP 레이어에서 강제적인 단편화(Fragmentation)가 발생하는데, 하위 소켓 드라이버에 단편화 조립 패킷 드롭 가드가 없어 **후반부에 배치된 오디오 특징량 슬롯 메모리 블록 전체가 유실된 채 전반부(진동)만 불완전 수신**되는 파이프라인 단절 틈새가 존재합니다.
 * **개선방향:** 패킷 구조체의 최대 물리 크기가 네트워크 안전 마진인 1400 bytes를 절대 넘지 않도록 다차원 배열 슬롯 크기를 재조정(Down-sizing)하거나, 통신 모듈 내부에서 MTU 크기 단위로 데이터 블록을 쪼개어 순차 번호를 매겨 송신하고 수신측에서 조립하는 응용 계층 단편화 제어 인터락(Application-level Packet Fragmentation Guard)을 구현할 것.

4대분류 10단계의 첫 번째 순서인 **Step 10-1 (바이트 패딩 불일치 및 이기종 간 엔디안 왜곡 검증)**에 집중하여, 구조체 오프셋 정렬 붕괴, 엔디안 오파싱에 의한 수치 폭발 및 MTU 경계 초과에 따른 오디오 데이터 유실과 관련된 치명적인 통신 레이어 틈새 3건을 완벽하게 도출했습니다.

 * **모듈:** T270_Commu
 * **문제점:** ESP32-S3 하드웨어 아키텍처는 리틀 엔디안(Little-Endian) 방식을 사용하는 반면, 표준 네트워크 통신 프로토콜 페이로드는 빅 엔디안(Big-Endian, Network Byte Order) 규격을 준수해야 합니다. 현재 통신 모듈의 소켓 버퍼 주입 루틴을 보면, 멀티바이트 필드(예: uint32_t sequence_loss_flag, float centroid)들에 대해 htons() 또는 htonl() 계열의 엔디안 변환 처리가 완전히 유실된 채 생(Raw) 바이트로 스트리밍하고 있습니다. 이로 인해 빅 엔디안 가이드를 따르는 수신측 시스템이 최상위/최하위 바이트 위치를 거꾸로 파싱하여 정상 데이터가 수억 배 부풀려진 기형적 수치로 왜곡됩니다.
 * **개선방향:** 바이트 패킹 직후 페이로드 헤더 및 정수형 데이터 필드에 대해 htonl() 복사 스왑 필터를 바인딩하고, 부동소수점(float) 데이터의 경우 IEEE 754 포맷의 바이트 시퀀스를 안전하게 역전시키는 전용 마이크로 스왑 매크로 함수(swapFloat())를 통신 레이어 종단에 주입할 것.
 * **번호:** 111 (신규 확인 이슈)
 * **모듈:** T215_Type / T270_Commu
 * **문제점:** 구조체 바이너리를 바이트 포인터(uint8_t*)로 강제 캐스팅하여 raw 소켓이나 MQTT 페이로드로 밀어 넣을 때 발생하는 전산학적 언더플로우 경계 예외입니다. 구조체의 총 바이트 크기인 sizeof(ST_Master_Packet_t) 연산 결과가 하드웨어 소켓 MTU(Maximum Transmission Unit, 통상 1500바이트) 한계선을 미세하게 초과하는 가변 패킷 확장 설계 오류가 존재합니다. 패킷 크기가 MTU 경계를 넘어서는 순간 IP 레이어에서 강제적인 단편화(Fragmentation)가 발생하는데, 하위 소켓 드라이버에 단편화 조립 패킷 드롭 가드가 없어 **후반부에 배치된 오디오 특징량 슬롯 메모리 블록 전체가 유실된 채 전반부(진동)만 불완전 수신**되는 파이프라인 단절 틈새가 존재합니다.
 * **개선방향:** 패킷 구조체의 최대 물리 크기가 네트워크 안전 마진인 1400 bytes를 절대 넘지 않도록 다차원 배열 슬롯 크기를 재조정(Down-sizing)하거나, 통신 모듈 내부에서 MTU 크기 단위로 데이터 블록을 쪼개어 순차 번호를 매겨 송신하고 수신측에서 조립하는 응용 계층 단편화 제어 인터락(Application-level Packet Fragmentation Guard)을 구현할 것.

## 4대분류. 통신 및 페이로드 엔지니어링 계층 (Commu & Payload Tier)
### 10단계: 직렬화 페이로드 인코딩 및 메모리 정렬 무결성 검증
#### 🎯 Step 10-2: 고속 스트리밍 시 RingBuffer 오버플로우로 인한 패킷 파편화 및 체크섬 무효화 추적
특징량 추출기에서 생성된 데이터가 네트워크 송신 전용 전역 링버퍼(TxRingBuffer)에 적재되고, 소켓 인터페이스를 통해 패킷화되어 나갈 때의 시간당 트래픽 임계치와 체크섬(Checksum) 연산의 무결성을 라인 단위로 추적했습니다.
 * **번호:** 112 (기존 #41 이슈 연계 및 확장)
 * **모듈:** T270_Commu
 * **문제점:** 오디오 프레임 주기(24.38ms)에 맞춰 초당 약 41회 격렬하게 호출되는 Commu::enqueueTx() 파이프라인에서, 네트워크 전송 전용 링버퍼(_txRingBuf)의 남은 잔여 공간(Free Space)을 검증하는 가드가 유실되어 있습니다. 현장 Wi-Fi 망의 일시적인 혼잡이나 AP 로밍(Handover) 지연으로 인해 소음/진동 결합 패킷의 송신 속도가 수 밀리초 단위로 지체될 때, 버퍼 헤드가 테일을 추월하는 **링버퍼 오버플로우(RingBuffer Overflow)가 발생하여 과거 패킷의 후반부와 신규 패킷의 전반부 메모리가 무작위로 뒤섞이는 페이로드 파편화 결함**이 존재합니다.
 * **개선방향:** 패킷 인입 전 반드시 if (ringbuf_get_free_size(_txRingBuf) < sizeof(ST_Master_Packet_t)) 예외 분기 가드를 두고, 공간 부족 시 가장 오래된 패킷을 명시적으로 드롭(Drop Oldest)하거나 송신 태스크의 우선순위를 동적으로 끌어올리는 버퍼 세이프티 인터락을 구현할 것.
 * **번호:** 113 (신규 확인 이슈)
 * **모듈:** T215_Type / T270_Commu
 * **문제점:** ST_Slot_Header_t 내부에는 패킷 변조 및 전송 오류를 필터링하기 위해 checksum 필드가 존재하지만, 이를 계산하는 Commu::calculateCRC16() 함수 내부의 포인터 연산에 치명적인 수학적 모순이 있습니다. 체크섬 구조적 한계선을 지정할 때 자기 자신인 checksum 필드 영역(2바이트)을 연산 대상에서 제외하지 않고 패킷 전체 크기(sizeof(ST_Master_Packet_t))를 그대로 주입하여 무결성을 구하고 있습니다. 이로 인해 **체크섬 결과값을 패킷 헤더에 대입하는 순간 패킷의 바이너리 상태가 물리적으로 변질되어, 수신측 게이트웨이 검증 통과 시 상시 '체크섬 오류(Invalid Checksum)'로 판정되어 패킷 전체가 영구 드롭**되는 인터락 모순이 존재합니다.
 * **개선방향:** CRC16 또는 Checksum 루프 연산의 유효 바이트 길이를 sizeof(ST_Master_Packet_t) - sizeof(p_packet.header.checksum)으로 엄격하게 격리 조치하고, 헤더 내 체크섬 필드 자리는 0x0000으로 프리클리어한 상태에서 순수 데이터 영역만 역산하도록 연산 마스킹 가드를 씌울 것.
 * **번호:** 114 (신규 확인 이슈)
 * **모듈:** T270_Commu / T290_FsmMgr
 * **문제점:** 고속 스트리밍 중 링버퍼 임계치 초과 또는 체크섬 에러가 누적되어 통신 패킷 드롭률이 런타임 기준치(예: 10 프레임 연속 유실)를 초과할 때 발생하는 시스템 상태 전이 인터락의 단절입니다. 통신 모듈은 내부의 전송 실패 플래그를 로컬 카운터로만 관리할 뿐, 이를 상위 FSM 매니저로 전달하지 않습니다. 이로 인해 장비 외형상으로는 정상 가동(RUN) 상태를 유지하지만, 실제로는 **네트워크 선로 단선으로 인해 진단 서버에 단 하나의 설비 결함 패킷도 도달하지 못하는 '침묵의 진단 불능(Silent Disconnection)' 상태**가 유포됩니다.
 * **개선방향:** Commu 엔진 내부에 연속 패킷 드롭 감시 카운터 가드를 신설하고, 임계치 도달 즉시 FSM 매니저에게 EM_StatusBit_t::COMMU_TX_BURST_FAULT 이벤트를 인터럽트 형태로 강제 격격 발송하여 시스템을 WARN_NET 또는 SAFE_FALLBACK 상태로 강제 천이시키는 예외 처리 시퀀스를 보완할 것.

## 4대분류. 통신 및 페이로드 엔지니어링 계층 (Commu & Payload Tier)
### 10단계: 직렬화 페이로드 인코딩 및 메모리 정렬 무결성 검증
#### 🎯 Step 10-3: JSON 직렬화/역직렬화(ArduinoJson V7.4.x) 시 힙 포인터 누수 및 파싱 타임아웃 검증
설비 설정 동기화 및 엣지 상태 진단을 위해 T220_CfgMgr 및 T270_Commu 레이어에서 사용되는 JSON 포맷팅 엔진(ArduinoJson V7.4.x)의 메모리 할당 정책과 부하 환경에서의 예외 가드를 라인 단위로 추적했습니다.
 * **번호:** 115 (기존 #41 이슈 연계 및 JSON 심화)
 * **모듈:** T220_CfgMgr / T270_Commu
 * **문제점:** ArduinoJson V7 아키텍처는 과거 V6의 DynamicJsonDocument 대신 JsonDocument 단일 구조체로 통합되었으며, 내부적으로 메모리 풀(Pool)을 동적으로 자동 확장(Reallocation)하는 메커니즘을 따릅니다. Commu::serializeStatusJson() 함수 내부에서 상태 패킷 변환을 위해 JsonDocument doc;을 고속 루프(24.38ms 주기) 내에 로컬 변수로 선언하여 사용하고 있으나, 특정 중첩 오브젝트(Nested Object)와 문자열 필드를 추가하는 과정에서 **메모리 풀 힙 포인터가 적절히 해제(Clear)되지 않고 파편화되어 RAM 영역을 매 초 수 킬로바이트씩 갉아먹는 메모리 누수(Memory Leak)** 틈새가 존재합니다. 이 현상이 누적되면 수 시간 내에 힙 메모리가 고갈되어 시스템이 강제 리셋됩니다.
 * **개선방향:** 로컬 JsonDocument 변수가 선언된 스코프가 종료되기 직전에 반드시 doc.clear(); 또는 doc.shrinkToFit();을 명시적으로 호출하여 내부적으로 재할당된 동적 메모리 블록을 완전히 힙 풀에 반환하도록 가드를 세울 것.
 * **번호:** 116 (신규 확인 이슈)
 * **모듈:** T220_CfgMgr
 * **문제점:** 웹 UI 또는 중앙 관제 서버로부터 새로운 설비 진단 파라미터 JSON 페이로드를 수신하여 CfgMgr::deserializeConfig()를 수행할 때, 유입되는 JSON 스트림의 문자열 길이 한계선(Length Boundary) 가드가 유실되어 있습니다. 악의적이거나 비정상적으로 거대한 크기(예: 수십 킬로바이트)의 손상된 JSON 패킷이 네트워크 포트를 통해 유입될 경우, deserializeJson() 함수는 힙 메모리가 바닥날 때까지 내부 포인터를 계속 확장하며 파싱을 시도합니다. 이는 곧바로 **메모리 할당 실패(Out of Memory) 커널 패닉을 유발하거나, 파싱 루프 내부에서 24.38ms의 오디오 수집 태스크 스케줄러 시간을 독점하여 워치독 타이머(WDT) 리셋을 유발**하는 치명적인 보안/구조적 결함입니다.
 * **개선방향:** JSON 파싱 함수 진입문 직전에 유입된 바이트 스트림의 원시 크기를 체크하는 검증식(if (inputLength > JSON_MAX_SIZE_LIMIT_BYTES))을 신설하고, 임계치 초과 시 즉각 파싱을 거부(Return Error)하는 입력 길이 제한 인터락을 인입할 것.
 * **번호:** 117 (신규 확인 이슈)
 * **모듈:** T215_Type / T220_CfgMgr
 * **문제점:** ArduinoJson을 통해 설정 파싱 성공(DeserializationError::Ok) 여부만 확인할 뿐, 파싱된 각 개별 필드의 데이터 타입 유효성(Type Validation) 및 물리적 하한/상한 경계 가드 검증이 완전히 유실되어 있습니다. 예를 들어, JSON 페이로드 내에 가속도 센서 윈도우 크기인 TENSOR_DEPTH_MAX 필드 값이 실수로 음수(-5)나 비정상적인 거대 정수(99999)로 유입되더라도, 설정 엔진은 이를 그대로 구조체 필드에 대입합니다. 이 오염된 파라미터가 후행 특징 추출 레이어(SeqBuilder)의 루프 카운터 상수로 바인딩되는 순간, 즉각적인 배열 인덱스 초과 오염(OOB Write) 커널 패닉으로 이어집니다.
 * **개선방향:** JSON 데시리얼라이즈 직후 각 필드별로 명시적 타입 캐스팅 검증식을 두고, p_cfg.audio.active_peak_count = doc["active_peak_count"].as<int>(); 등 변환 후 반드시 std::clamp를 사용하여 지정된 물리적 안전 범위 내부의 값만 최종 구조체 슬롯에 투영하도록 세이프티 가드를 추가할 것.

#### 🎯 Step 11-1: MQTT 클라이언트 연결 유실(LWT) 시 FSM 재기동 시퀀스와 센서 수집 독점 블로킹 인터락 점검

### 11단계: 네트워크 예외 및 가용 자원 한계 제어 가드 검증
#### 🎯 Step 11-2: Wi-Fi AP 연결 이탈 시 소켓 좀비화 방지용 킵얼라이브(Keep-Alive) 및 하드웨어 복구 시퀀스 검증

 * **번호:** 121
 * **모듈:** T270_Commu
 * **문제점:** ESP32-S3의 LwIP 소켓 레이어에서 Wi-Fi 물리 링크가 끊어졌을 때, 응용 계층의 MQTT 클라이언트 패킷 송신 루틴(pubSubClient.loop())이 세션 단선을 즉각 인지하지 못하는 '하위 링크-상위 소켓 동기화 유실' 결함이 존재합니다. 킵얼라이브(Keep-Alive) 상수가 수십 분 단위의 OS 기본값으로 방치되어 있어, 물리 링크가 복구되더라도 기존 소켓이 힙 메모리에 좀비 상태로 박혀 포트를 점유(Socket Stuck)합니다. 이로 인해 새롭게 유입되는 실시간 소음/진동 특징량 데이터 패킷이 버퍼 외부로 나가지 못하고 지속적으로 드롭되는 치명적인 전송 마비 틈새가 존재합니다.
 * **개선방향:** Commu 초기화 구문에 LwIP 소켓 옵션 제어 API(setsockopt)를 바인딩하여 SO_KEEPALIVE, TCP_KEEPIDLE (예: 5초), TCP_KEEPINTVL (예: 1초), TCP_KEEPCNT (예: 3회) 상수를 런타임에 강제 주입하는 하드웨어 소켓 가드를 이식할 것.
 * **번호:** 122 (신규 확인 이슈)
 * **모듈:** T200_Main / T270_Commu
 * **문제점:** Wi-Fi 연결 이탈을 감지하는 이벤트 핸들러(WiFiEvent_t) 내부의 예외 처리 로직이 단순 WiFi.begin() 재호출 구조로만 짜여 있어 발생하는 하드웨어 내부 레지스터의 데드락 예외입니다. ESP32-S3 Wi-Fi 서브시스템(RF 내부 MAC 레이어)이 강한 산업용 EMI 노이즈로 인해 하드웨어 락업(Lock-up) 상태에 빠지면, 소프트웨어적인 재시작 명령은 아무런 효과가 없습니다. 이 상태에서 가드가 없으면 무한히 실패하는 재연결 인터럽트만 발생하여 CPU 코어 자원을 독점하고, 결국 실시간 특징 추출(24.38ms) 파이프라인의 실시간성 타이밍 윈도우를 영구 파괴합니다.

 * **번호:** 123 (신규 확인 이슈)
 * **모듈:** T270_Commu / T290_FsmMgr
 * **문제점:** 네트워크 전파 불포화로 인해 통신 모듈이 Wi-Fi 재연결 및 소켓 복구 루틴을 격렬하게 수행하는 동안, FSM 매니저가 기계 결함 상태(EM_SystemState_t::FAULT) 전이 명령을 수신했을 때 발생하는 통신 스레드 독점 모순입니다.  * **문제점:** 현장 조율 중 사용자가 새로운 설비 설정값을 적용하여 비휘발성 플래시 영역에 저장하는 saveConfiguration() 가동 시, 저장 공간 부족(Flash Full)이나 쓰기 타임아웃 오류가 발생했을 때의 방어 누락입니다. 파일에 데이터가 절반만 기록된 채 쓰기 연산이 비정상 종료(Partial Write)되면, 기존 정합성이 유지되던 설정 파일마저 찢겨 나가며 텍스트 포맷이 완전히 깨지게 됩니다. 이 상태로 장비가 현장에서 정전 등의 이유로 재부팅되면, 다음 기동 시 파싱 엔진(ArduinoJson)이 영구 파싱 불가 상태(Invalid JSON)를 뱉으며 장비가 무한 부팅 루프(Boot-loop) 컨텍스트에 갇히게 됩니다.
 * **개선방향:** 변경된 설정을 기존 파일에 직접 덮어쓰지 말고, 임시 Swap 파일(config.tmp)에 먼저 완전 기록을 마친 뒤, 무결성 검증(Checksum 및 크기 대조) 가드를 통과한 엣지 시점에만 기존 원본 파일을 원자적으로 교체(Rename) 처리하는 2단계 트랜잭션 저장 스키마(Atomic File Swap Guard)를 이식할 것.
 * **번호:** 126 (신규 확인 이슈)
 * **모듈:** T220_CfgMgr / T290_FsmMgr
 * **문제점:** 플래시 하드웨어 자체의 물리적 파손(셀 마모 및 배드 섹터)으로 인해 설정값 로드 및 폴백 구조가 완전히 무효화되는 최하위 하드웨어 예외 장벽입니다. CfgMgr이 파일 시스템 하드웨어 예외를 포착했음에도 상위 FSM 매니저와 물리 경보 회로로 심각한 하드웨어 에러 신호를 송출하지 않습니다. 시스템은 내부 연산 파라미터가 영(0) 또는 난수로 오염된 상태에서 무리하게 모터 진단(RUN) 상태 전이를 강행하게 되며, 이는 곧 **핵심 TinyML 추론 및 룰베이스 세이프티 가드가 완벽히 무력화된 무방비 상태로 공장 생산 라인이 상시 가동되는 물리적 보안 사고**로 직결됩니다.
 * **개선방향:** 파일 시스템 마운트 및 트랜잭션 복구 시도가 최종 실패할 경우, 런타임 제어권을 완전히 상실한 것으로 간주하여 FSM 매니저에게 EM_StatusBit_t::FLASH_HARDWARE_DEAD 결함 이벤트를 강제 발송하고, 하드웨어 릴레이 및 경보 경광등을 즉각 강제 차단 고정(Safe Mode Shutdown Lock)하는 최종 방어 벽을 구성할 것.
