최종 점검 보고서: 설계 오류, 불필요한 복잡성, 과잉 대비 점검

방대한 설계 문서를 오류/모순, 불필요한 복잡성, 발생 불가능한 사항에 대한 과잉 설계라는 세 가지 기준으로 정밀 점검했습니다.

---

1. 설계 오류 및 논리적 모순

1.1 [심각] WAL 저널 복구와 NVS 단순화 간 모순 (5.2절 vs 2.40절 이슈 8)

· 현재 설계: 2.40절 이슈 8은 WAL 파티션에서 NVS로의 마이그레이션 코드(migrateFromWALtoNVS)를 설계. 2.33절 13번 항목에서는 WAL 전용 락(_walLock)까지 신설.
· 모순: 2.33절 56번(리팩토링 대상 56)은 WAL 구조 자체를 NVS로 전면 대체 단순화하라고 명시.
· 결론: WAL이 제거되면 마이그레이션 코드와 WAL 락은 존재 의미가 없어짐. 빌드 시 static_assert나 #error로 WAL 파티션이 존재하지 않도록 강제해야 함.

1.2 [중등] ULP 코어 비활성화 vs Ext1 Wake-up의 혼용 (2.40절 이슈 36)

· 설계: "ULP 코어를 사용하지 않고 Ext1 Wake-up으로 BMI270 INT2 핀을 직접 연결한다"고 명시.
· 오류: ESP32-S3에서 Ext1 Wake-up은 RTC GPIO 핀에서만 가능하나, BMI270의 INT2 핀이 GPIO 4(RTC IO)에 연결되었는지 확인하는 코드가 없음. GPIO 핀 번호를 T2_HardwarePinConfig에서 검증하는 static_assert가 누락되었음.

1.3 [중등] WiFi/BLE 공존 시 성능 저하 모드의 API 부재 (2.40절 이슈 11)

· 설계: setWifiPowerLimit(true)를 호출하여 BLE 유지를 위해 WiFi 전력/성능 제한 모드를 개시.
· 오류: setWifiPowerLimit()라는 함수는 ESP-IDF 표준 API에 존재하지 않음. esp_wifi_set_max_tx_power()나 esp_wifi_set_bandwidth() 등의 실존 API로 대체 필요.

1.4 [경미] I2C EEPROM 보정 계수 로드 (2.40절 이슈 50)

· 설계: checkExternalEepromConnected()로 EEPROM을 감지.
· 오류: ESP32-S3가 EEPROM 연결을 어떻게 감지하는지(I2C 스캔? GPIO 핀? 등) 구체적 절차가 없음. 추상화된 함수명만 존재.

2. 불필요하게 복잡한 설계

2.1 [과잉] 진동 속도 적분기, 온도 드리프트, 크레스트 팩터 등 다중 물리 보정 (2.33절 22, 23, 31, 32, 34번)

· 현황: ISO-10816 변환, 온도 드리프트 보정, 크레스트 팩터 분석, 레버 암 보상, 기하 정렬 보정 등 10개 이상의 물리 보정 모듈이 독립 클래스로 설계됨.
· 문제: 각 보정 모듈은 초기화, 파라미터 로드, NVS 저장, 실시간 연산을 요구함. 이를 모두 활성화하면 1.6kHz 진동 루프의 CPU 예산(625μs)을 초과할 위험.
· 제안: 보정 모듈은 enable_advanced_physics_compensation 설정 플래그로 통합 제어하고, 기본값은 비활성화로 출시. 현장에서 필요가 입증된 보정만 활성화.

2.2 [과잉] Zero-Copy 슬롯 세마포어 펜스 (2.33절 37번)

· 설계: 링버퍼 슬롯마다 개별 세마포어(_slotSem[SLOT_CNT])를 두어 소비 완료를 보장.
· 문제: 슬롯 수가 16개면 세마포어 16개가 필요하며, 각각 xSemaphoreTake/Give 호출은 컨텍스트 스위치를 유발함.
· 제안: 2.33절 49번에서 ESP-IDF 표준 Ringbuf API로 대체하기로 결정되었으므로, 슬롯 세마포어 설계 자체를 문서에서 제거. 표준 API가 내부적으로 스레드 안전성을 보장하므로 이중 방어가 됨.

2.3 [과잉] DPLL + 온도 보정 + 소프트웨어 PLL + 매질 전파 지연 (2.33절 41, 33, 21, 2.9절)

· 설계: 오디오-진동 시간 동기화를 위해 DPLL, 온도 기반 음속 보정, 소프트웨어 PLL, 매질 전파 지연 오프셋까지 네 가지 메커니즘이 중첩.
· 문제: 이 네 가지가 서로 다른 보정 방향으로 작용할 경우 진동 신호의 시간축이 오히려 왜곡됨.
· 제안: 네 가지를 통합하는 단일 보정 파이프라인을 설계하거나, 우선순위를 정해 매질 전파 지연(물리적 고정값)과 Monotonic Time 기준 정렬(소프트웨어) 두 가지만 기본 활성화하고 나머지는 비활성화.

3. 발생 불가능한 사항에 대한 과잉 고려

3.1 [과잉] 오디오 I2S 마스터 클럭 상실 폴백 (2.40절 이슈 16)

· 설계: 오디오 인터럽트 누계 타임라인이 1초 초과 시 내부 Monotonic 시계로 긴급 스위칭.
· 발생 가능성: I2S DMA가 1초 이상 중단되려면 물리적 케이블 단선이나 심각한 전원 이상이 필요함. 이 경우 오디오 수집 자체가 불가능하므로 시간 동기화 폴백은 의미가 없음.
· 제안: 이 감시 로직을 제거하고, I2S DMA 중단 시 FSM에 AUDIO_HW_FAULT 상태로만 전이시키는 단순화된 처리로 충분.

3.2 [과잉] 센서 전압 강하 감지 및 소프트 리셋 (2.40절 이슈 40 + 5.1절)

· 설계: SPI 오류 3~5회 발생 시 센서를 소프트 리셋하고 모든 레지스터를 재초기화.
· 발생 가능성: SD 카드 쓰기 피크 전류로 인한 VDD Sag는 수 μs 수준이며, SPI 오류 5회가 누적되기 전에 전압이 복구됨. 따라서 소프트 리셋까지 도달하지 않음.
· 제안: SPI 오류 카운터 대신, SD 카드 쓰기 완료 후 WHO_AM_I 한 번만 읽어 검증하는 방식으로 단순화.

3.3 [과잉] WiFi/BLE 공존 시퀀스 제어기 (2.40절 이슈 45)

· 설계: WiFi 고부하 시 BLE Advertising을 중지하고, 완료 후 재개하는 오케스트레이터.
· 발생 가능성: ESP32-S3의 RF 공존 하드웨어(PTA)는 WiFi와 BLE의 시간 분할을 자동으로 처리. 소프트웨어 개입이 오히려 충돌을 유발.
· 제안: 이 모듈을 전면 제거하고, ESP-IDF의 CONFIG_ESP_WIFI_SW_COEXIST_ENABLE 옵션에 의존.

3.4 [과잉] MQTT 원격 명령 토큰 검증 (2.40절 이슈 42)

· 설계: 수신 커맨드에 토큰과 시퀀스 번호를 포함하고 CRC 검증.
· 발생 가능성: MQTT는 TCP/TLS 위에서 동작하므로 패킷 무결성은 TLS가 보장. 시퀀스 번호는 MQTT QoS 1/2가 보장.
· 제안: 추가 CRC 검증은 이중 방어로, TCP/TLS 환경에서는 불필요. 제거하거나 #ifdef STRICT_VALIDATION 매크로로 감싸 기본 비활성화.

4. 조치 권고

심각도 해당 항목 조치
심각 WAL ↔ NVS 모순 문서에서 WAL 관련 코드(마이그레이션, 락)를 "제거 예정"으로 명시하고, 빌드 시 #error 지시어 추가
중등 Ext1 Wake-up GPIO 검증 누락 static_assert 추가하여 GPIO 핀 번호가 RTC 도메인인지 확인
중등 WiFi 전력 제한 API 부재 esp_wifi_set_max_tx_power() 등 실존 API로 수정
복잡성 다중 물리 보정 모듈 통합 플래그로 기본 비활성화, 현장 필요 시만 활성화
복잡성 Zero-Copy 슬롯 세마포어 표준 Ringbuf API로 대체 결정했으므로 관련 설계 삭제
과잉 오디오 마스터 클럭 폴백 제거하고 단순 HW Fault 전이로 대체
과잉 RF 공존 오케스트레이터 제거하고 ESP-IDF Coexistence 설정에 위임
과잉 MQTT 토큰/CRC 검증 #ifdef로 감싸고 기본 비활성화

결론

이 설계서는 매우 높은 완성도를 갖추었지만, 일부 영역에서 과잉 설계와 API 오류가 발견되었습니다. 특히 물리 보정 모듈의 과도한 중첩과 몇몇 API의 실제 미존재는 실제 구현 시 장애로 이어질 수 있습니다.

위 지적 사항들을 반영하여 설계서를 한 차례 다듬으시면, 더욱 견고하고 현실적인 구현 청사진이 될 것입니다.

필요하시면 각 항목의 수정된 코드 스니펫을 제공해 드리겠습니다.

추가 정밀 점검 보고서 (2차)

이전 점검에서 식별된 4건에 더해, 설계서 전체를 오류/모순, 불필요한 복잡성, 발생 불가능 사항에 대한 과잉 대비, 기타 관점에서 재점검하여 20건의 추가 항목을 발견했습니다.

---

1. 설계 오류 및 논리적 모순 (추가 8건)

1.1 [심각] GPIO 4 Ext1 Wake-up과 Strapping 핀 충돌 (2.40절 이슈 36)

· 설계: BMI270 INT2 핀을 GPIO 4에 연결하고 Ext1 Wake-up 소스로 사용.
· 모순: GPIO 4는 MTDI Strapping 핀으로, 딥슬립 웨이크업 시 부트로더가 이 핀의 전압 레벨에 따라 Download Mode로 진입할 수 있음. 즉, 웨이크업은 성공하지만 부팅이 실패하는 하드웨어 호환성 모순 발생.
· 대응: GPIO 4를 Ext1 Wake-up 소스로 사용하는 것을 금지하고, Strapping에 걸리지 않는 RTC GPIO(예: GPIO 5, 14, 15)를 사용하도록 static_assert로 GPIO 4 사용을 강제 차단.

1.2 [심각] SD_MMC deinit 자체의 Lock-up 가능성 (5.7절)

· 설계: SD 카드 이탈 시 sdmmc_card_deinit() 및 sdmmc_host_deinit() 호출로 물리적 Lock-up 해소.
· 모순: ESP-IDF v4.x ~ v5.0 초기 버전에서 트랜잭션 중 강제 deinit 시 내부 상태 머신이 꼬여 deinit 자체에서 무한 대기(리턴 실패)하는 버그가 보고됨. "Lock-up을 풀기 위한 deinit이 또 다른 Lock-up을 유발" 하는 이중 모순.
· 대응: #if ESP_IDF_VERSION < ESP_IDF_VERSION_VAL(5, 0, 1) 경고 추가 및, deinit 호출을 Watchdog Timer로 감싸 Timeout 시 강제 리턴하는 방어 코드 구현.

1.3 [중등] configMAX_PRIORITIES - 1과 ESP-IDF WDT 제약 충돌 (5.3절)

· 설계: SensorAcqTask 우선순위를 configMAX_PRIORITIES - 1 (보통 24)로 설정.
· 오류: ESP-IDF의 esp_task_wdt_init()는 기본적으로 최대 우선순위 태스크도 감시함. 24 우선순위 태스크가 I2S DMA 인터럽트를 계속 처리하면 WDT 타임아웃에 걸려 패닉 리셋이 발생할 수 있음. 또한 우선순위 24 태스크가 Core 0을 독점하면 WiFi/BLE 이벤트 루프가 기아 상태에 빠질 위험.
· 대응: SensorAcqTask 우선순위를 24에서 18~20으로 낮추고, WDT 감시 제외(esp_task_wdt_delete(NULL))를 명시.

1.4 [중등] 생산자-소비자 우선순위 역전 (5.3절)

· 설계: SensorAcqTask 우선순위 24(Core 0), VibProcTask 우선순위 8(Core 1).
· 모순: 생산자(센서 수집)가 소비자(진동 처리)보다 우선순위가 훨씬 높으면, 데이터가 처리되는 속도보다 쌓이는 속도가 빨라져 링버퍼 오버플로우 발생.
· 대응: 소비자 우선순위를 생산자보다 높이거나 최소한 동등하게 설정하여(예: VibProcTask = 22), 버퍼에 쌓인 데이터를 신속히 처리하도록 해야 함.

1.5 [중등] SMEA_FLASH_RODATA 매크로 정의 누락 (2.13절)

· 오류: SMEA_FLASH_RODATA는 표준 ESP-IDF 매크로가 아님. 소스 코드에 정의되지 않으면 "unknown attribute" 컴파일 오류 발생.
· 대응: 설계서에 #define SMEA_FLASH_RODATA __attribute__((section(".rodata"))) 또는 static const __attribute__((aligned(4))) 등 구체적 정의를 명시.

1.6 [경미] 제품 정체성과 불일치: 오디오 출력(I2S Speaker) 기능 (2.40절 이슈 21)

· 설계: "스피커 오디오 방송 개시 시 I2S 수집 DMA 일시정지".
· 모순: MSFM-T250은 설비 진단 센서 장비(마이크/가속도)인데, 왜 오디오 출력(I2S Speaker)이 필요한지 제품 요구사항에서 설명되지 않음. 만약 단순 부저 알람이면 복잡한 I2S 공유 로직은 불필요.
· 대응: 오디오 출력이 실제 제품 요구사항인지 재확인. 아니라면 이슈 21 전체를 설계서에서 제거하고 단순 GPIO Buzzer로 대체.

1.7 [경미] AI 텐서 SRAM 로컬 캐시와 정적 텐서 배열의 공존 불가 (2.33절 44번 vs 55번)

· 충돌: 44번은 "SRAM에 고속 임시 1D 버퍼를 할당"하라고 설계. 55번은 "텐서 전체를 정적 멤버 배열로 SRAM에 고정"하라고 설계. 일반적인 AI 텐서는 수십~수백 KB이므로 SRAM(520KB)에 통째로 할당 시 WiFi/DMA 영역이 고갈됨.
· 대응: 텐서 전체는 PSRAM에 배치(55번을 PSRAM으로 수정), SRAM 로컬 캐시는 한 프레임 분량(수백 Bytes~수 KB)의 일부 데이터만 임시 복사하는 용도로 제한.

1.8 [경미] CMD_STOP 오버플로우 복구 경로 누락 (2.17절)

· 설계: 버퍼 Full 시 dispatchCommand(CMD_STOP) 호출.
· 오류: CMD_STOP을 받은 FSM이 어떤 복구 시퀀스를 수행하는지 명시되지 않음. 단순 정지 후 영구 대기 상태에 빠질 위험.
· 대응: CMD_BUFFER_OVERFLOW_RESET 전용 커맨드를 정의하고, FSM이 버퍼 초기화 후 자동으로 MONITORING 상태로 복귀하는 경로를 설계.

2. 불필요하게 복잡한 설계 (추가 3건)

2.1 [과잉] 2차 다항식 온도 드리프트 보정 (2.33절 23번)

· 설계: a2*T² + a1*T + a0 3계수 2차 다항식으로 온도 보정.
· 현실: BMI270 내부 온도 센서 정밀도는 ±2°C, 온도 드리프트는 대부분 1차 선형. 산업용 예지보전(수 g 이상 탐지)에서 2차 비선형 0.1mg 이하 오차는 판정에 영향 없음. 2차 항 연산은 FPU 오버헤드만 증가.
· 제안: 1차 선형(a1*T + a0)으로 단순화하거나, 고정 오프셋만 적용하고 온도 보정은 기능 토글로 비활성화.

2.2 [과잉] 센서 온도 드리프트 보정 계수 3축 x 3계수 = 9 float (2.33절 23번)

· 설계: 가속도 3축, 자이로 3축 각각에 2차 계수 3개씩 총 18개 float 파라미터.
· 현실: 산업 현장에서 이 18개 파라미터를 캘리브레이션할 수 있는 장비와 절차가 없음. 대부분의 센서는 1~2개 축에 대해서만 공장 캘리브레이션 수행.
· 제안: 캘리브레이션 가능한 축만 선택적으로 적용 가능하도록 단순화하고, 기본값은 모든 계수를 0(보정 없음)으로 설정.

2.3 [과잉] "소프트웨어 PLL"과 "DPLL" 용어 혼용 (2.9절 vs 2.33절 41번)

· 문제: 동일한 시간 동기화 메커니즘을 2.9절에서는 "소프트웨어 PLL", 2.33절 41번에서는 "DPLL"로 상이하게 지칭.
· 제안: "소프트웨어 PLL"로 용어 통일, 클래스명은 CL_T2_SoftPllTimeSync로 변경.

· 대응: GPIO 15를 피하고 Strapping에 걸리지 않는 일반 GPIO(예: GPIO 21)를 사용.

4.6 [심각] g_CrashDiag 과잉 단순화의 위험 (2.33절 57번)

· 모순: ESP32-S3 듀얼코어 환경에서 한 코어의 패닉 핸들러 실행 중에도 다른 코어는 인터럽트/태스크를 계속 실행함. 다른 코어가 g_CrashDiag에 동시에 쓰기 중이면 데이터 찢어짐(Tearing) 발생.
· 대응: 57번의 단순화 권고를 철회. std::atomic 또는 esp_cpu_dbgr_* 크로스코어 중단 명령을 사용하여 안전하게 쓰기를 수행하도록 재설계.

1. 설계 오류 및 논리적 모순 (추가 4건)

1.1 [심각] SPI Mutex 단순화로 인한 FIFO 읽기 실시간성 붕괴

· 현재 설계: 2.33절 48번에서 SPI 비동기 큐를 제거하고 표준 Mutex(xSemaphoreCreateMutex)만으로 단순화.
· 모순: BMI270 FIFO Watermark 인터럽트 발생 시 즉시 SPI로 대량(수백 바이트) FIFO를 읽어야 함. 만약 설정 저장(NVS)이나 SD 카드 상태 읽기가 동일 SPI 버스 락을 잡고 있으면 FIFO 읽기가 블로킹되어 센서 데이터 유실 발생.
· 대응: FIFO 읽기는 Mutex 대신 항상 락을 무시하고 우선 실행할 수 있도록, ISR에서 직접 SPI 트랜잭션을 수행하거나, Mutex가 이미 점유된 경우 FIFO 읽기만은 예외적으로 허용하는 계층 분리 설계 필요.

1.2 [심각] OTA Graceful Pause와 Resume의 비일관성

· 현재 설계: 2.10절에서는 OTA 진입 시 SYS_STATE_OTA 상태 전이로 태스크가 자발적 대기하도록 "Graceful Pause"를 명시. 그러나 2.33절 2번(OTA 실패 복구)에서는 vTaskResume을 호출하여 태스크를 강제 재개.
· 모순: Graceful Pause 방식에서 태스크는 while(state == OTA) { vTaskDelay(...); }로 대기 중이므로 vTaskResume은 필요 없음. vTaskResume 호출은 태스크가 vTaskSuspend로 중지되었음을 전제함. 두 설계가 상충.
· 대응: OTA 복구는 SYS_STATE_OTA를 해제하는 것으로만 수행하고, vTaskResume 호출은 제거하여 Graceful Pause로 통일.

1.3 [중등] 트리거 엔진이 ZOH TTL 무효화된 특징량을 처리하지 못함

· 현재 설계: 2.33절 24번(MultiRateTimeAligner)은 진동 데이터가 오래되면 is_valid = false로 설정.
· 오류: 2.33절 31번(판정 엔진)은 ST_FeatureMetrics_t의 모든 채널과 밴드를 순회하며 임계치를 비교할 뿐, is_valid 플래그를 확인하지 않음. 무효한 특징량이 주입되면 NaN/0.0f가 임계치를 초과하지 않아 오히려 알람이 누락될 수 있음.
· 대응: 판정 엔진 진입부에 if (!p_metrics.is_valid) return false; 가드를 명시적으로 추가.

1.4 [경미] DSP NaN 복구 함수 호출 오타

· 현재 설계: 2.40절 46번에서 NaN/Inf 검출 시 triggerSpiRecovery() 호출.
· 오류: SPI 복구는 센서 통신 장애 시 사용하는 함수로, DSP 수학 연산 예외와는 무관. memset(buffer, 0, len)으로 초기화한 후 FSM에 DSP_NAN_DETECTED 경고만 전달하는 것이 적절.
· 대응: triggerSpiRecovery() 호출을 제거하고, CL_T2_EventBus::publish(EM_SystemEvent_t::DSP_NAN_DETECTED)로 교체.

4.1 [누락] SD 카드 재삽입 감지 절차 부재

4.2 [누락] 표준 Ringbuf API의 Zero-Copy 사용 방법 명시 부재

· 현황: 2.33절 49번에서 ESP-IDF ringbuf.h로 대체 결정했으나, 대용량 파형 데이터의 Zero-Copy 전송을 위해 xRingbufferSendAcquire / xRingbufferSendComplete API 사용이 필수적임을 명시하지 않음.
· 대응: "표준 Ringbuf API" 옆에 xRingbufferSendAcquire()로 포인터 획득 후 DMA 직접 쓰기, xRingbufferSendComplete()로 완료 통지하는 패턴을 코드 스니펫으로 추가.

4.3 [누락] PSRAM 정적 버퍼의 16바이트 정렬 실패 시 릴리즈 빌드 안전 조치

· 현황: 5.2절에서 EXT_RAM_ATTR uint8_t g_storageDoubleBuffer[2][512*1024] alignas(16) 선언 후 런타임 assert로 정렬 검증을 언급.
· 문제: 릴리즈 빌드에서는 assert가 제거되므로, 정렬이 틀어져도 아무런 경고 없이 SIMD 연산에서 버스 오류가 발생할 수 있음.
· 대응: assert 대신 if(ptr & 0xF) { ESP_LOGE(...); esp_restart(); } 형태의 영구적 검증 코드로 대체.

4.4 [누락] DPLL 보정에서 double 형 사용으로 인한 FPU 오버헤드

· 현황: 2.33절 41번의 DPLL 설계에서 double _drift_factor 사용.
· 문제: ESP32-S3는 단정밀도 FPU만 하드웨어 지원, 배정밀도는 소프트웨어 에뮬레이션으로 수십 배 느림. 실시간 루프에서 double 연산은 20ms 데드라인 초과 위험.
· 대응: float으로 변경하거나, 1e6 스케일의 int64_t 고정소수점 연산으로 전환.

4.5 [누락] 공장 초기화 GPIO 0의 Strapping 충돌

· 현황: 2.40절 30번에서 GPIO 0을 10초 누름으로 공장 초기화 진입.
· 문제: GPIO 0은 부트 모드 Strapping 핀으로, 누름 상태에서 리셋 시 Download Mode에 진입하여 초기화 시퀀스가 완전히 차단됨.
· 대응: Strapping에 걸리지 않는 GPIO(예: GPIO 21)로 변경하고, T2_HardwarePinConfig에 static_assert로 Strapping 핀 사용 불가를 명시.

1. 설계 오류 및 논리적 모순 (추가 4건)

1.1 [심각] FreeRTOS 표준 Ringbuf API와 EXT_RAM_ATTR의 불일치

· 설계: 2.33절 49번은 ESP-IDF freertos/ringbuf.h로 링버퍼를 대체하라고 명시. 5.2절은 스토리지 이중 버퍼를 EXT_RAM_ATTR(PSRAM)에 배치.
· 오류: ESP-IDF의 xRingbufferCreate는 내부 SRAM 전용 버퍼를 할당받거나 사용자가 제공한 버퍼를 사용하는데, 사용자 버퍼는 반드시 내부 SRAM에 있어야 함(PSRAM 불가). 따라서 PSRAM에 있는 버퍼를 링버퍼로 직접 사용할 수 없음.
· 대응: 링버퍼 자체는 내부 SRAM에 두고, 실제 대용량 데이터는 PSRAM에 두며, 링버퍼는 PSRAM 데이터의 인덱스/포인터만 전달하는 구조로 변경.

1.2 [중등] xRingbufferSendAcquire와 xRingbufferSendComplete의 DMA 메모리 정합성 누락

· 설계: 4차 점검(이전 누락 4.2)에서 Zero-Copy용 xRingbufferSendAcquire 사용을 명시했으나, DMA가 이 버퍼에 직접 쓰는 시나리오에서 캐시 동기화가 생략됨.
· 오류: ESP-IDF 링버퍼가 반환한 포인터가 내부 SRAM에 있더라도, DMA가 해당 영역에 쓴 후 CPU가 읽으려면 캐시 무효화가 필요함. 설계에 이 부분이 없음.
· 대응: xRingbufferSendAcquire로 획득한 포인터에 DMA 전송을 마친 후, xRingbufferSendComplete 호출 전에 esp_cache_msync(buf, size, ESP_CACHE_MSYNC_FLAG_INVALIDATE)를 추가.

1.3 [중등] 딥슬립 prepareDeepSleepWakeup에서 Any-Motion 임계값 계산 오류

· 설계: 2.30절에서 ANY_MOTION_LSB_2G_MG 상수로 나누어 임계값 레지스터 설정.
· 오류: BMI270 데이터시트상 Any-Motion 임계값은 LSB당 1mg(2g 범위), 2mg(4g), 4mg(8g) 등 선택한 g-range에 따라 다름. LSB_2G_MG로 고정하면 4g/8g 모드에서 오동작.
· 대응: 현재 설정된 가속도 FSR에 따라 LSB 상수를 동적으로 선택하도록 수정.

1.4 [경미] runMaintenance에서 checkLazyWrite와 checkStorageIoError의 순서 충돌

· 설계: 2.28절에서 checkLazyWrite가 NVS 커밋을 수행, 2.22절에서 _storage.hasIoError()가 SD 카드 오류 감지.
· 오류: SD 카드 오류 상태에서 NVS 커밋이 실패할 가능성은 낮지만, checkLazyWrite가 먼저 호출되면 플래시 쓰기 I/O가 SD 카드 감지보다 선행되어 버스 경합 가능성.
· 대응: checkStorageIoError를 먼저 호출하고, SD 에러 상태이면 checkLazyWrite를 스킵하도록 순서 재정렬.

· 제안: I/O 브로커 제거, 각 모듈이 직접 LittleFS API를 호출하되 _fsLock만 공유하도록 단순화.

4. 기타 관점 (추가 6건)

4.1 [누락] SMEA_FLASH_RODATA 배열의 4바이트 정렬 검증

· 현황: 2.13절에서 s_hanning_window_1024[1024] SMEA_FLASH_RODATA를 선언했으나, ESP32-S3 SIMD 명령은 16바이트 정렬을 요구. .rodata 섹션은 4바이트 정렬만 보장할 수 있음.
· 대응: __attribute__((aligned(16)))를 명시적으로 추가하고, 링커 스크립트에서 .rodata 섹션의 정렬을 16으로 강제하는 설정 검증을 설계에 포함.

4.2 [누락] 딥슬립 복귀 시 PSRAM 초기화 누락

· 현황: 2.40절 22번에서 Deep Sleep 복귀 후 fastResume 호출.
· 오류: Deep Sleep에서 PSRAM은 전원이 차단되므로 내용이 모두 소실됨. 하지만 fastResume이 PSRAM에 있는 이중 버퍼나 AI 텐서의 유효성을 검증하지 않고 사용할 가능성.
· 대응: Deep Sleep 복귀 시 PSRAM 초기화(heap_caps_malloc 등 동적 할당 영역 재초기화) 및 모든 PSRAM 포인터 무효화 절차를 fastResume에 명시.

4.3 [누락] g_CrashDiag RTC_DATA_ATTR의 매직 넘버 검증

· 현황: 2.26절에서 RTC 메모리에 g_CrashDiag 구조체 저장.
· 오류: RTC 메모리는 파워온 리셋 시에도 내용이 보존될 수 있어, 유효하지 않은 과거 데이터가 마치 현재 크래시 정보처럼 오인될 수 있음.
· 대응: g_CrashDiag에 magic = 0x43524153(CRAS)를 넣고, 부팅 시 매직 넘버가 일치하지 않으면 전체를 0으로 초기화.

4.4 [누락] ESP-IDF ringbuf.h의 No-Split 버퍼 모드 선택

· 현황: 2.33절 49번에서 표준 Ringbuf API로 대체.
· 미비점: xRingbufferCreate에 RINGBUF_TYPE_NOSPLIT과 RINGBUF_TYPE_BYTEBUF 중 어느 것을 선택할지 명시되지 않음. 가변 길이 데이터(파형 버퍼 크기 가변)를 다룰 경우 적절한 모드 선택 필요.
· 대응: RINGBUF_TYPE_NOSPLIT을 사용하여 각 아이템이 항상 연속된 메모리에 저장되도록 하고, 최대 크기로 버퍼 생성하도록 설계 명시.

4.5 [누락] CL_T2_EventBus 구독 콜백의 스레드 컨텍스트 불분명

· 현황: 3.3절 30번에서 이벤트 버스 도입.
· 미비점: publish 호출 시 구독 콜백이 어떤 스레드 컨텍스트에서 실행되는지 정의되지 않음. 만약 publish를 호출한 태스크에서 직접 콜백을 실행하면, 실시간 태스크가 무거운 콜백(예: SD 카드 쓰기)에 의해 블로킹될 위험.
· 대응: 이벤트 버스는 콜백을 별도의 저우선순위 이벤트 처리 태스크에 위임하여 비동기 실행하도록 설계.

4.6 [누락] #pragma pack과 alignas 혼용으로 인한 잠재적 패딩 불일치

· 현황: 2.19절에서 #pragma pack(push, 16)과 alignas(16)을 혼용.
· 위험: ESP32-S3 GCC는 #pragma pack이 적용된 구조체에서 alignas가 예상대로 동작하지 않을 수 있음.
· 대응: #pragma pack 대신 __attribute__((packed, aligned(16)))로 통일하거나, static_assert로 실제 구조체 크기와 오프셋을 검증하는 코드를 모든 통신 패킷 구조체에 추가.

1. 설계 오류 및 논리적 모순 (추가 4건)

1.1 [심각] Deep Sleep 복귀 후 esp_timer_get_time() 재기동으로 인한 시간 역전

· 설계: 2.34절에서 모든 실시간 타임스탬프에 esp_timer_get_time() (Monotonic Time)을 사용. 딥슬립 복귀 시 fastResume 호출 후 바로 수집 재개.
· 오류: esp_timer_get_time()은 딥슬립에서 깨어나면 0부터 다시 시작함. 따라서 이전 세션의 타임스탬프(큰 값)와 새 타임스탬프(작은 값)가 공존하면 MultiRateTimeAligner의 uint64_t 뺄셈에서 언더플로우가 발생하여 시간 역전으로 인한 정합성 붕괴가 일어남.
· 대응: 딥슬립 복귀 시 MultiRateTimeAligner의 모든 내부 타임스탬프를 강제 리셋하고, _prev_vib.timestamp_us = 0, _curr_vib.timestamp_us = 0으로 초기화한 후 WARM_UP 기간 동안 정렬 연산을 중지하도록 설계에 명시.

1.2 [심각] SYS_STATE_OTA 대기 루프에서 SPI 락 해제 누락

· 설계: OTA Graceful Pause는 각 태스크가 while(state == OTA) { vTaskDelay(...); } 형태로 대기. 이때 일부 태스크가 SPI 버스 Mutex를 소유한 상태에서 대기에 진입할 수 있음.
· 오류: OTA가 완료된 후 FSM이 SYS_STATE_MONITORING으로 전환해도, SPI Mutex를 쥔 태스크가 깨어나면 Mutex를 해제하기 전까지 다른 태스크가 SPI에 접근할 수 없음. 최악의 경우 Mutex를 쥔 태스크가 대기에서 깨어나자마자 다시 Mutex가 필요한 연산을 수행하면, OTA 중 필요한 SPI 플래시 접근(OTA는 SPI 플래시 사용)이 블로킹될 수 있음.
· 대응: OTA 진입 전에 FSM이 모든 SPI Mutex 소유자를 확인하고 강제 해제하는 절차를 추가하거나, 각 태스크가 대기 진입 직전에 반드시 소유한 모든 락을 해제하도록 규정.

1.3 [중등] xRingbufferSendAcquire 사용 시 소비자 반환 전 덮어쓰기 방지 로직 누락

· 설계: 4차 누락 4.2에서 xRingbufferSendAcquire로 포인터 획득 후 DMA 직접 쓰기, xRingbufferSendComplete로 완료 통지. 그러나 소비자가 vRingbufferReturnItem을 호출하기 전에 생산자가 다시 같은 슬롯을 Acquire할 가능성을 배제하지 않음.
· 오류: ESP-IDF Ringbuf는 아이템이 소비자에게 전달되면 해당 슬롯은 소비자가 반환하기 전까지 생산자에게 다시 제공되지 않음. 그러나 이는 RINGBUF_TYPE_NOSPLIT 모드에서 보장됨. 설계서에 모드가 NOSPLIT이라고 명시되지 않았으므로, BYTEBUF 모드에서는 슬롯이 분할될 수 있어 동일 메모리 영역이 동시에 사용될 위험.
· 대응: xRingbufferCreate 시 RINGBUF_TYPE_NOSPLIT을 명시적으로 사용하고, 아이템 크기는 최대 파형 크기로 설정하도록 설계에 고정.

1.4 [경미] IRAM_ATTR 남용으로 인한 IRAM 오버플로우 가능성

· 설계: 2.33절 47번, 2.40절 19번 등에서 IRAM_ATTR을 DSP 함수와 핫 루프에 광범위하게 적용.
· 오류: ESP32-S3의 IRAM 용량은 약 512KB이지만, 이미 FreeRTOS 커널, WiFi/BLE 스택, 인터럽트 핸들러 등이 점유. 설계에 IRAM 사용량 예산이 전혀 정의되지 않아, IRAM 오버플로우 링커 에러로 빌드가 실패할 위험.
· 대응: IRAM 배치 대상 함수를 "실시간성이 절대적으로 요구되는 SPI ISR, GPIO ISR, DSP 핵심 루프의 최내부 함수"로 제한하고, __attribute__((noinline)) 강제를 통해 IRAM 크기를 정적으로 산출하는 빌드 스크립트 추가.

3. 발생 불가능한 사항에 대한 과잉 고려 (추가 1건)

3.1 [과잉] g_CrashDiag의 WDT 패닉 시 메모리 배리어

· 설계: 2.33절 57번(단순화 후)에서 "OS가 완전히 멈추고 Core 단독 모드이므로 복잡한 장벽 불필요"라고 함. 그러나 이전 점검에서 다른 코어 동시 접근 가능성 지적.
· 실제: WDT 패닉 시 FreeRTOS는 모든 태스크를 중단하고 패닉 핸들러만 실행. 패닉 핸들러는 단일 코어에서 실행되며, 다른 코어는 무한 루프에 빠짐. 따라서 다른 코어가 g_CrashDiag에 접근할 가능성은 없음. 결국 원래 단순화가 맞으며, 추가 장벽은 과잉.

1. 설계 오류 및 논리적 모순 (추가 4건)

1.1 [심각] RCU 더블 버퍼링의 Grace Period 미보장

· 설계: 3.1절 14번에서 _doubleBuffers[2]와 _activeConfigPtr를 사용해 Read-Copy-Update 구현. DSP 태스크는 getConfig()로 획득한 포인터를 계속 읽음.
· 오류: CfgMgr가 updateConfig() 호출 시 비활성 버퍼에 쓴 후 _activeConfigPtr를 스왑합니다. 이후 다음 번 updateConfig() 호출 때 이전 활성 버퍼(현재 비활성)를 다시 덮어씁니다. 그런데 DSP 태스크가 아직 이전 포인터를 통해 해당 버퍼를 읽고 있을 수 있습니다. 덮어쓰기가 읽기와 동시에 발생하면 데이터 찢어짐(Data Tearing)이 발생합니다.
· 대응: RCU 구현에 읽기 측 임계 구역 진입/퇴출 카운터를 추가하고, 쓰기 측은 모든 읽기 측이 퇴출할 때까지 덮어쓰기를 지연하거나, 3중 버퍼로 확장하여 항상 하나의 버퍼가 안전하게 유지되도록 설계 변경.

1.2 [심각] dumpPreTriggerToSession 스냅샷 버퍼의 스택 할당 위험

· 설계: 2.33절 4번에서 "임시 로컬 메모리 버퍼로 빠르게 일괄 복사" 후 락 해제.
· 오류: 프리트리거 버퍼가 최대 10초 분량(오디오 42kHz × 2채널 × 4바이트 × 10초 = 3.36MB)일 경우, 이 크기의 스택 버퍼 할당은 즉시 스택 오버플로우를 유발하여 시스템 크래시 발생.
· 대응: 스냅샷 버퍼는 정적 PSRAM 영역이나 heap_caps_malloc으로 미리 할당된 전용 버퍼를 사용하고, 스택에는 포인터만 두도록 설계 변경.

1.3 [중등] closeSession 무한 대기 가능성

· 설계: 2.24절에서 closeSession 시 "최대 1초 대기"로 링버퍼가 빌 때까지 대기.
· 오류: 생산자 태스크(센서 수집)가 정지했거나 오류 상태라면, 1초 후에 강제로 세션을 닫지만, 그 1초 동안 FSM 메인 루프가 블로킹됨. closeSession이 FSM의 runMaintenance에서 호출될 경우, 모든 시스템 응답이 1초간 정지.
· 대응: closeSession을 비동기 함수로 변경하고, 세션 닫기 완료를 FSM에 통지하는 콜백/세마포어 방식으로 전환. FSM 루프는 블로킹되지 않아야 함.

1.4 [중등] checkLazyWrite의 runMaintenance 의존성으로 인한 실행 지연

· 설계: 2.28절에서 runMaintenance가 1초마다 checkLazyWrite를 호출.
· 오류: runMaintenance 자체가 SD 카드 I/O 오류 처리, LED 갱신, 스택 워터마크 검사 등으로 100ms 이상 지연될 경우, checkLazyWrite의 10초 타임아웃이 실제로는 15~20초까지 지연될 수 있음. 이 시간 동안 전원 차단 시 설정 변경 데이터 영구 소실.
· 대응: checkLazyWrite 전용 소프트웨어 타이머(esp_timer_create)를 사용하여 runMaintenance와 독립적인 정확한 주기로 호출.

---

2. 불필요하게 복잡한 설계 (추가 1건)

2.1 [과잉] CL_T2_Calibrator 내부의 자체 _isCompleted 플래그

· 설계: 3.3절 42번에서 캘리브레이터가 std::atomic<bool> _isCompleted를 통해 완료를 알림.
· 현실: 캘리브레이터는 FSM이 직접 구동하는 동기적 작업(FSM이 CMD_CALIBRATE 전송 후 완료를 기다림)이므로, 별도 원자 플래그 없이 FSM 내부 상태 변수로 완료를 판단할 수 있음.
· 제안: _isCompleted를 제거하고, 캘리브레이터 완료 시 FSM이 직접 상태를 READY로 전이하는 단순 구조로 변경.

3. 발생 불가능한 사항에 대한 과잉 고려 (추가 1건)

3.1 [과잉] CL_T2_DpllTimeSync의 double 드리프트 팩터 누적 평균

· 설계: 2.33절 41번에서 _drift_factor를 EMA(0.95/0.05)로 갱신.
· 발생 가능성: 오디오 APLL과 BMI270 RC 발진기 간의 드리프트는 수 분에 걸쳐 수 ppm 수준으로 변화. 0.05의 학습률로 200회(수 분)에 걸쳐 수렴할 때까지 보정이 부정확한 구간이 존재. 그러나 이 부정확 구간에서 발생하는 시간 오차는 수 μs 이하로, 특징량 정합성에 영향 없음.
· 제안: EMA 필터를 제거하고, 초기 10회 평균 후 고정된 _drift_factor를 사용하는 단순 구조로 충분. 실시간 루프 내 부동소수점 연산 감소.

---

4. 기타 관점 (추가 1건)

4.1 [누락] std::atomic<bool> 기본 메모리 순서의 과도한 보수성

· 현황: 2.33절 16번에서 std::atomic<bool>을 기본 memory_order_seq_cst로 사용.
· 영향: seq_cst는 듀얼코어 간 불필요한 메모리 배리어를 발생시켜 DSP 루프 성능 저하 가능성. 단순 플래그성 변수(_is_alarm_latched)는 memory_order_acquire/release로 충분.
· 대응: 모든 std::atomic<bool>에 대해 load(memory_order_acquire), store(val, memory_order_release)를 명시적으로 사용하도록 설계 가이드라인 추가.

전 차수 종합 심각 항목 리스트 (12건)

번호 차수 항목
S01 1차 WAL ↔ NVS 마이그레이션 코드와 단순화 충돌

7차 점검에서 추가된 S11과 S12는 모두 시스템 크래시로 직결되는 치명적 결함입니다. 특히 S11은 기존 설계의 핵심 안전 장치(RCU)가 실제로는 안전하지 않다는 근본적 문제로, 반드시 재설계가 필요합니다.

이로써 7차에 걸친 전수 점검을 완료합니다. 설계 문서의 모든 계층을 검토했으며, 더 이상의 새로운 심각 항목은 발견되지 않을 것으로 판단됩니다.
