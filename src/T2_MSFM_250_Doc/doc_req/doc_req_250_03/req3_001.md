현재 T290_FsmMgr_250 코드를 다시 한번 검토했습니다.
전반적으로 정교하게 설계되어 있지만, 아래와 같이 안정성·유지보수성·버그 방지 측면에서 다듬을 수 있는 부분들이 눈에 띕니다.

1. ⚠️ 버그 가능성 – OTA 복구 시 잘못된 ISR 핸들러 연결

```cpp
void CL_T2_FsmManager::resumeFromOtaFailure() {
    // ...
    extern void T200_handleTriggerISR();
    attachInterrupt(..., T200_handleTriggerISR, RISING);  // ❌
}
```

문제점:
실제 ISR 핸들러는 T2_90_IMU_watermark_isr()로 변경되었는데, OTA 복구 시 이전 함수명(T200_handleTriggerISR)을 그대로 사용하고 있습니다.
이로 인해 OTA 후 인터럽트가 걸리면 미정의 동작이 발생합니다.

제안:
T2_90_IMU_watermark_isr로 통일합니다.

```cpp
attachInterrupt(digitalPinToInterrupt(PIN_INT1_WATERMARK_CONST),
                T2_90_IMU_watermark_isr, RISING);
```

2. 메모리 할당 실패 처리 누락

init()에서 각종 heap_caps_aligned_alloc / heap_caps_malloc을 호출한 뒤 성공 여부를 검사하지 않고 바로 memset 등을 수행합니다.
메모리 부족 상황에서 접근하면 크래시로 이어집니다.

제안:
모든 할당 후 nullptr 체크를 하고, 실패 시 return false 또는 ESP_LOGE 후 정리하는 방어 로직이 필요합니다.

---

3. s_pInstance 초기화 순서 안전장치

```cpp
static CL_T2_FsmManager& getInstance() {
    static CL_T2_FsmManager v_inst;
    s_pInstance = &v_inst;   // 호출 시점에 저장
    return v_inst;
}
```

getInstance()를 통해야만 s_pInstance가 설정되는 구조인데, 혹시나 전역 객체 초기화 시점에서 ISR이 먼저 동작할 가능성은 거의 없지만, 혹시 모를 상황에 대비해 s_pInstance를 명시적으로 nullptr로 초기화하는 코드가 현재 빠져 있습니다.

제안:
클래스 선언 외부에서 정적 멤버를 명시적으로 초기화해주면 더 안전합니다.

```cpp
// 전역 스코프에서
CL_T2_FsmManager* CL_T2_FsmManager::s_pInstance = nullptr;
```

4. _stopReasonCmd 변수의 동시성

dispatchCommand() (주로 메인 스레드)와 runMaintenance()에서 _stopReasonCmd를 읽고 쓰지만, 별도의 락이나 atomic으로 보호되지 않았습니다.
다중 코어 환경에서 동시성 문제가 생길 수 있습니다.

제안:
std::atomic<uint8_t>로 변경하거나, _stopReasonCmd 접근부에 portENTER_CRITICAL을 추가합니다.

---

5. broadcastTelemetryPayload의 하드코딩된 배열 크기

```cpp
std::copy(p_vib.accel.band_energy[0], p_vib.accel.band_energy[0] + 16, ...);
v_pkt.gyro_rms_energy[0] = p_vib.gyro.band_energy[0][0];
v_pkt.gyro_rms_energy[1] = p_vib.gyro.band_energy[0][1];
std::copy(p_aud.audio.timbre_bands, p_aud.audio.timbre_bands + 32, ...);
std::copy(p_aud.mfcc, p_aud.mfcc + 13, ...);
```

숫자 16, 32, 13 등이 매직 넘버로 박혀 있습니다.
T2_Def 또는 T2_Type에 정의된 상수와 불일치할 경우 버퍼 오버런이 발생할 수 있습니다.

제안:
해당 길이가 정의된 enum이나 constexpr이 있다면 그것을 사용하고, 없으면 static_assert로 구조체 크기를 검증하십시오.

v_tmpAud.sample_rate = CL_T2_ConfigManager::getInstance().getConfig().audio.sample_rate;

함수 진입 시 이미 const auto& v_cfg = ...로 받아오면 호출 비용과 가독성이 개선됩니다.

7. _imuAcqTask 종료 후 핸들 초기화

```cpp
detachInterrupt(...);
v_this->_hImuAcqTask = nullptr;
vTaskDelete(NULL);
```

ISR에서 s_pInstance->_hImuAcqTask를 검사한 후 vTaskNotifyGiveFromISR을 호출하는데, nullptr로 세팅하는 순서가 detachInterrupt 이후이므로 이미 인터럽트가 분리된 상태에서 nullptr 참조는 안전합니다.
하지만 만약 detachInterrupt가 실패하거나 지연된다면?
방어적으로 인터럽트를 분리한 후에 _hImuAcqTask를 nullptr로 만들기 전에 짧은 critical section을 주는 것도 고려할 수 있습니다. (현재는 크게 문제 없음)

---

8. runMaintenance()의 딥슬립 진입 조건

딥슬립 진입 시 PIN_BTN_CONTROL_CONST, PIN_INT2_MOTION_CONST가 하드웨어 정의에 없을 경우 컴파일 오류가 발생할 수 있습니다.

제안:
#ifdef 또는 if constexpr로 해당 핀이 정의되지 않은 환경에서도 컴파일되도록 가드 처리.

---

9. 매직 넘버 정리

ISR에서

```cpp
if (v_ccount - v_last_ccount > 120000) { ... }
```

120000이 0.5ms를 의미하는 것으로 보이나, CPU 클록에 종속적입니다.
CONFIG_ESP32_DEFAULT_CPU_FREQ_MHZ 등을 이용해 계산하거나, 명확한 상수로 정의하는 것이 좋습니다.

태스크 내 vTaskDelay(pdMS_TO_TICKS(24)), pdMS_TO_TICKS(10) 등도 의미 단위로 매크로화하면 가독성이 향상됩니다.

---

10. 예외 안전성 (RAII 도입 검토)

heap_caps_malloc으로 할당한 버퍼들을 raw 포인터로 관리하고, 소멸자에서 수동으로 해제합니다.
중간에 함수가 실패할 경우 누수가 발생할 수 있으므로 std::unique_ptr에 커스텀 deleter를 사용하거나, ScopeGuard 패턴을 적용하면 더 안전해집니다.
