도메인별 변수 구조체화 및 도출된 개선 항목(1-1 ~ 5-4)을 실제 코드에 안전하게 반영하기 위한 체계적 설계 및 실행 계획임.

1~5단계 개선 항목과 실제 도출된 설계 코드를 교차 검증한 결과, 일부 누락 및 설계 범위가 축소(약화)된 8가지 항목을 식별하여 이에 대한 보완 설계를 아래와 같이 최종 병합 및 반영함.

## [추가] 교차 검증에 따른 설계 누락 및 축소/약화 사항 식별 (최종)

### 1. 설계 누락 사항 (Omissions)

* **[누락 1] 스토리지 매니저(`T260`)의 원시 소음 버퍼(`_preAudRawBuf`) 매핑 누락**
  * **원인**: 2단계 구조체 치환 과정에서 `_preAudBuf`와 `_preAudRawBuf` 중 `_preAudRawBuf`에 대한 템플릿 제어 블록화가 누락됨.
  * **영향**: 고장 트리거 발생 시 사고 전후 상황을 복원하는 '타임머신 레코딩'에서 DSP 필터링 이전의 원시 소음(Raw Audio) 블랙박스 파일이 정상적으로 저장되지 않을 위험이 있음.

* **[누락 2] SPSC 링버퍼(`T216`) 페이로드 정렬 가드(Guard) 코드 누락**
  * **원인**: 4단계에서 링버퍼 페이로드 정합성을 '검토'만 하고, 실제 제로 카피(Zero-Copy) 안전성을 강제하는 코드를 템플릿 내부에 삽입하지 않음.
  * **영향**: 향후 링버퍼에 전달되는 구조체가 변경되어 16바이트 정렬이 깨지더라도 컴파일 타임에 이를 차단하지 못해 런타임 메모리 예외가 발생할 수 있음.

* **[누락 3] 캘리브레이션 엔진(`T280`) 및 센서 적용부(`T230`) 동기화 누락**
  * **원인**: 2단계에서 `T230`의 개별 변수(`_accOffsetX` 등)를 `_accParams` 구조체로 병합했으나, 이 오프셋 값을 계산하는 `T280_Calibrator` 모듈과 설정 파일에서 값을 불러오는 `T230`의 `applyStoredAccelCalibration()` 내부 연산 로직을 구조체 매핑으로 전환하는 작업이 계획에서 누락됨.
  * **영향**: 자동 캘리브레이션 완료 후 갱신된 영점(Zero-point) 데이터가 센서 엔진 구조체에 주입되지 않아, 공장 초기값으로 계속 동작하는 치명적인 진단 오차가 발생함.

* **[누락 4] RTC(딥슬립/웜부팅) 복구용 상태 변수 속성 매핑 누락**
  * **원인**: `T200_Main`에 구현된 WDT 크래시 복구 및 딥슬립 로직은 특정 변수를 `RTC_DATA_ATTR`로 선언하여 메모리를 유지함. 개별 상태 변수(`_lastAccX` 등)를 1단계에서 일반 구조체(`ST_ImuAxisParams_t`)로 무분별하게 통합하면서 RTC 메모리 보존 속성이 상실됨.
  * **영향**: 배터리 모드(시나리오 B)에서 딥슬립 웨이크업 시 또는 WDT 웜부팅 시, 이전 DSP 필터의 딜레이 스테이트(Delay State)가 모두 증발하여 재부팅 직후 파형 왜곡 및 오경보가 발생함.

### 2. 설계 축소 및 약화 사항 (Reductions)

* **[축소 1] 코어 파이프라인 데이터 상수성(Const-Correctness) 약화**
  * **원인**: 1단계에서 구조체(`ST_ImuAxisBuf_t`) 내부 포인터를 입력/출력 공용으로 쓰기 위해 `float*`로 통일함. 3단계에서 파라미터로 넘길 때 `const ST_ImuAxisBuf_t&`를 사용했으나, 이는 껍데기(구조체)만 상수로 만들 뿐 내부 포인터가 가리키는 데이터의 수정은 막지 못함.
  * **영향**: 데이터 읽기 전용이어야 할 특징량 추출 엔진(`T245`) 등에서 프로그래머의 실수로 원시 데이터를 덮어쓰면, 이를 백그라운드에서 저장하는 SD 카드 파일의 무결성이 훼손될 수 있음.

* **[축소 2] 비휘발성 설정 마이그레이션(`T220`)의 과격한 복구 정책**
  * **원인**: 5단계에서 매직넘버 검증 실패 시 기존 포맷(JSON 등)을 살려보려는 시도 없이 즉각 공장 초기화(`resetToDefault()`)를 강제 전이하도록 설계함.
  * **영향**: 펌웨어 OTA 업데이트 시 현장 실무자가 공들여 튜닝한 노치 필터 계수, 알람 임계치 등 현장 맞춤형 파라미터가 영구 삭제되어 재설치 공수가 크게 발생함.

* **[축소 3] `ST_ImuAxisParams_t` 사이즈 최적화에 따른 SIMD 정렬 붕괴 (36바이트의 함정)**
  * **원인**: 1단계 설계 시 패딩 바이트 누수를 막기 위해 float 9개로 구성된 구조체를 정확히 36바이트로 맞춤. 단일 객체로는 문제가 없으나, 36은 16(SIMD 캐시라인)의 배수가 아님.
  * **영향**: 이 구조체를 배열(예: `_params[2]`)로 할당하거나 16바이트 정렬이 강제되는 링버퍼 페이로드에 싣게 되면, 두 번째 요소의 메모리 주소가 16배수에서 어긋남. 즉각적인 하드웨어 예외(`LoadStoreError`) 및 시스템 패닉을 유발함. 48바이트로 패딩을 강제(`alignas(16)`)해야 함.

* **[축소 4] 텐서 시퀀스 빌더(`T248`) 내 오프셋 활용의 불완전성**
  * **원인**: 4단계에서 도메인별 메모리 주소 추적을 위해 `_offsetMap` 구조체를 도입하여 `calculateOffsets()`를 개선함. 그러나 정작 텐서를 복사하는 `buildFlattenTensor()` 구현부 내부에는 여전히 매직넘버와 하드코딩된 사이즈 연산(`p_targetTensor + AUD_FEAT_CNT`)이 잔존함.
  * **영향**: 향후 AI 모델의 MFCC 차원 수나 진동 피처 개수가 변경될 경우, `_offsetMap`은 정상 갱신되지만 하위 복사 로직이 하드코딩되어 있어 텐서 메모리 오버플로우나 세그멘테이션 폴트(Segfault)가 발생함.

```cpp
// T220_CfgMgr_250.cpp (로드 실패 시 과격한 초기화 대신 JSON 파싱 시도)
bool CL_T2_CfgManager::load() {
    File v_file = LittleFS.open("/cfg/master.bin", "r");
    if (!v_file) {
        ESP_LOGW(TAG, "Config file not found. Applying default settings.");
        resetToDefault();
        return false;
    }

    uint32_t v_savedMagic = 0;
    v_file.read((uint8_t*)&v_savedMagic, sizeof(uint32_t));
    size_t v_expectedSize = sizeof(uint32_t) + sizeof(T2_Type::ST_DynamicConfig_t);

    // [보완 적용 - 축소 2 해결] 점진적 설정 마이그레이션 적용
    if (v_savedMagic != T2_CFG_MAGIC_NUMBER || v_file.size() != v_expectedSize) {
        ESP_LOGW(TAG, "Binary layout mismatch. Attempting to parse legacy JSON format...");
        v_file.close();

        // 기존 설정 파일(JSON)을 열어 구조체 필드별 매핑 시도 후 저장 (실패 시에만 초기화)
        if (!_recoverFromLegacyJson()) {
            resetToDefault();
        }
        return true;
    }

    // 검증 통과 시 정상 로드 진행
    v_file.read((uint8_t*)&_currentConfig, sizeof(T2_Type::ST_DynamicConfig_t));
    v_file.close();
    return true;
}
```

### 3. 구조체 리팩토링 총평 및 마무리

* 도메인별 변수 통합 작업을 통해 4-Tier 아키텍처의 데이터 응집도가 대폭 상승함.
* 함수 파라미터 전달 비용이 최소화되었으며, 설계 보완을 통해 상수성 보장 및 링버퍼 메모리 예외 발생 가능성을 컴파일 타임에 원천 차단함.
* SIMD 캐시라인 정렬 강제(`alignas(16)`)와 RTC 데이터 보존 정책을 추가함으로써, 웜부팅/딥슬립 환경에서의 필터 안정성을 확보하고 ESP32 아키텍처 상의 런타임 하드웨어 패닉 오류 가능성을 원천적으로 배제함.
