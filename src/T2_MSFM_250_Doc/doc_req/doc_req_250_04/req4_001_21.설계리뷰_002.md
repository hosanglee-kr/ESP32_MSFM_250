### 1. 구조적 결함 및 논리적 모순 (Structural Defects & Logical Contradictions)

* **[결함 1] `esp_cache_msync` 캐시 라인(Cache Line) 정렬 위반 및 오버헤드**
* **문제점**: ESP32-S3의 데이터 캐시 라인은 32바이트(또는 64바이트)임. `esp_cache_msync` API는 대상 주소와 동기화 사이즈가 반드시 캐시 라인의 배수여야 정상 동작함. `_preAudCtrl.capacity * sizeof(...)` 연산 결과가 32의 배수가 아닐 경우 `ESP_ERR_INVALID_ARG`를 반환하며 동기화가 실패함.
* **해결책**: 동기화 사이즈를 캐시 라인 크기 단위로 올림(Round-up) 처리하는 매크로 또는 연산 로직이 필수적임.


* **[결함 2] SPSC 링버퍼(`T216`) 정렬 가드의 논리적 모순**
* **문제점**: 보완 설계에서 `static_assert(alignof(T) >= 4)`를 추가했으나, 이는 단순 32비트 포인터 정렬만 검증할 뿐 SIMD 가속기가 요구하는 16바이트 정렬을 보장하지 못함. 배열 요소 하나가 16바이트 정렬을 위반하면 여전히 하드웨어 패닉이 발생함.
* **해결책**: `alignof(T) % 16 == 0` 조건을 강제하거나, 페이로드 전체 크기가 16의 배수인지 검증하는 가드로 상향해야 함.


* **[결함 3] 텐서 시퀀스 빌더(`T248`) 내부 버퍼 오버플로우 위험 잔존**
* **문제점**: `std::copy`를 사용하여 동적 오프셋 기반 복사를 수행하도록 개선했으나, `_offsetMap.audio_offset + p_audioFeatCnt`가 `_nn_input_boundary`를 초과하는지 검사하는 바운더리 체크가 누락됨.
* **해결책**: 복사 수행 직전 목적지 버퍼의 남은 공간을 확인하는 안전 가드를 삽입해야 함.



### 2. 로직 누락 및 타 모듈 영향도 미고려 (Missing Logic & Cross-Module Impacts)

* **[누락 1] RTC 메모리 상태 보존(`T200`)과 DSP 엔진(`T240`) 간의 캡슐화 붕괴**
* **문제점**: `g_rtc_imu_state`를 `T200_Main_250.cpp`에 전역 변수로 분리 선언했으나, 실제 필터링을 수행하는 `CL_T2_DspEngine`이 이 전역 변수를 어떻게 참조하고 갱신할지에 대한 인터페이스 매핑 설계가 누락됨. 클래스 내부에서 전역 변수를 직접 호출하면 객체 지향의 캡슐화가 파괴되고 코드 결합도가 비정상적으로 높아짐.
* **해결책**: DSP 엔진 초기화 시 RTC 상태 버퍼의 포인터 또는 참조를 외부에서 주입(Dependency Injection)받도록 설계해야 함.


* **[누락 2] 파이프라인 함수(`processAccel`, `extractAccel`)의 데이터 흐름 모순**
* **문제점**: 4단계 스케줄러 보완 코드(`VibProcTask`)를 보면 `extractAccel`에 `v_accInBuf`(원시 데이터)를 주입하고 있음. 특징량 추출은 필터를 거친 정제된 데이터(`v_accOutBuf`)를 기반으로 수행해야 정상임. 또한 `processAccel`의 입력 파라미터가 `const ST_ImuAxisBufConst_t&`가 아닌 기존 `ST_ImuAxisBuf_t&`로 남아 있어 상수성 보장 규격이 엇갈림.
* **해결책**: 입력과 출력의 인터페이스 규격을 명확히 분리하고, 파이프라인 간 데이터 전달 흐름을 교정해야 함.


* **[누락 3] 레거시 JSON 파싱(`T220`) 시 동적 메모리(OOM) 고갈 대비 누락**
* **문제점**: 과격한 초기화를 막기 위해 `_recoverFromLegacyJson()`을 도입했으나, OTA 직후 힙 메모리(SRAM) 단편화가 심한 상태에서 크기가 큰 JSON 파일 전체를 파싱하려고 시도하면 `ArduinoJson` 파서가 메모리 할당에 실패하여 시스템이 크래시(Crash)될 수 있음.
* **해결책**: JSON 파싱 시 스택(Stack) 메모리를 제한적으로 사용하거나, PSRAM을 파서용 메모리 풀로 강제 지정하는 방어 로직이 필요함.

이전 분석에서 도출된 메모리/통신/자료구조 레벨의 결함을 넘어, **실시간 운영체제(RTOS) 스케줄링, 데이터 파이프라인의 물리적 정합성, 하드웨어 예외 처리(Hardware Failsafe)** 관점에서 시스템을 심층 재점검했습니다.

그 결과, 실제 산업 현장에서 설비 오작동이나 펌웨어 크래시를 유발할 수 있는 **5가지 치명적인 심층 결함(Deep Defects)** 을 추가로 식별했습니다.

---

### 1. 데이터 파이프라인 및 DSP 정합성 결함 (DSP & Pipeline Integrity)

* **[결함 7] 링버퍼 데이터 유실(Drop) 시 시계열 불연속성에 의한 가짜 고장(False Alarm) 폭주**
* **원인**: `T216_RingBuf`는 락프리(Lock-free) 구조로 버퍼가 꽉 차면 데이터를 버림(Drop). 만약 Core 1의 태스크가 밀려 Core 0의 I2S/SPI 수집 데이터가 유실된 후 다음 데이터가 이어 붙으면, 물리적으로 연속되지 않은 파형이 연결됨.
* **영향**: 불연속적인 파형에 FFT를 수행하면 '스펙트럴 리키지(Spectral Leakage)' 현상이 발생하여 고주파 대역에 거대한 팝/클릭(Pop/Click) 노이즈가 생성됨. 이로 인해 `피크 주파수` 및 `첨도(Kurtosis)` 수치가 비정상적으로 튀어, 멀쩡한 설비의 전원을 차단(Interlock)하는 대형 사고가 발생함.
* **해결책**: 데이터 드롭 발생 시 DSP 엔진에 플래그를 전달하여 **이전 필터 상태(Delay State) 및 히스토리를 강제 초기화(Reset)하고, 해당 윈도우 프레임의 특징량 추출을 스킵(Muting)** 해야 함.


* **[결함 8] NTP 동기화에 따른 시간 도약(Time Jump) 시 미분 특징량(Delta Feature) 발산**
* **원인**: `T210_Def_250.hpp`의 `get_monotonic_timestamp_us()`는 로컬 타이머에 NTP 오프셋(`g_MonotonicTimeOffsetUs`)을 더하여 반환함. 주기적인 NTP 동기화로 오프셋이 갑자기 몇 초 단위로 점프할 수 있음.
* **영향**: 시간 변화량(`dt`)을 분모로 사용하는 델타 특징량 연산이나 가속도의 속도/변위 적분 과정에서, 시간 점프가 발생하면 연산 결과가 무한대(NaN/Inf)로 발산함. 시스템은 이를 심각한 설비 파손으로 오인하여 즉각 알람을 발생시킴.
* **해결책**: DSP 연산 및 미분/적분에는 **오직 순수 하드웨어 단조 타이머(`esp_timer_get_time()`)만을 사용**하고, NTP가 보정된 시간은 파일 저장 및 텔레메트리 패킷의 타임스탬프(Tagging) 용도로만 엄격히 분리해야 함.



### 2. RTOS 동시성 및 FSM 제어 결함 (Concurrency & Control)

* **[결함 9] SPI 버스 뮤텍스에 의한 우선순위 역전 (Priority Inversion) 데드락**
* **원인**: `T230_Sensor`에서 멀티코어 접근 방지를 위해 `_spiLock`을 사용함. 만약 하위 우선순위 태스크(예: 통신 태스크)가 설정값을 읽기 위해 `_spiLock`을 잡고 있는 도중, 최상위 우선순위 12인 `ImuAcqTask`가 깨어나 SPI를 요청하면 대기 상태에 빠짐.
* **영향**: 이때 중간 우선순위 태스크들이 CPU를 선점하면, 하위 태스크가 `_spiLock`을 반환하지 못해 `ImuAcqTask`가 영원히 블로킹(Starvation)됨. 이는 결국 링버퍼 고갈 및 WDT 리셋으로 이어짐.
* **해결책**: `_spiLock`을 일반 세마포어가 아닌 **우선순위 상속(Priority Inheritance)을 지원하는 Mutex (`xSemaphoreCreateMutex()`)로 명시적 생성**해야 함.


* **[결함 10] `WARM_UP` 상태 중 Trigger 엔진 억제 로직 누락**
* **원인**: 부팅 직후 센서 안정화를 위해 `WARM_UP` 상태를 도입했으나, `T250_TriggerEngine::runDiagnostic` 함수 내부에는 현재 FSM 상태가 `WARM_UP`인지 확인하여 룰 검사를 우회하는 가드 로직이 없음.
* **영향**: 부팅 직후 DC 오프셋이 채 제거되지 않은 쓰레기(Garbage) 데이터가 트리거 엔진에 흘러 들어가면, `WARM_UP`이 끝나기도 전에 알람이 발송되고 강제 레코딩 상태로 상태 머신이 꼬여버림.
* **해결책**: 트리거 엔진 내부 또는 파이프라인 호출부에서 **FSM 상태가 `MONITORING`일 때만 판정을 수행하도록 인터락(Interlock) 처리**해야 함.



### 3. 하드웨어/스토리지 페일세이프 (Hardware Failsafe)

* **[결함 11] SD 카드 무단 탈거(Hot-Swap) 시 VFS 블로킹에 의한 시스템 마비**
* **원인**: `T260_Storage`는 `flush()` 및 `fwrite()`를 수행함. 쓰기 작업 중 현장 작업자가 SD 카드를 무단 탈거하면, ESP32의 FATFS 하위 드라이버는 버스 응답을 기다리며 최대 수 초 이상 태스크를 블로킹(Blocking)함.
* **영향**: `StorageTask`가 `_fsLock`을 잡은 상태로 블로킹되면, 이 락을 대기하는 FSM 상태 전환 로직이나 설정 저장 로직까지 도미노처럼 멈춰 시스템 전체가 벽돌(Hang) 상태가 됨.
* **해결책**: 물리적인 **SD Card Detect (CD) 핀을 하드웨어 인터럽트로 연결**하여, 탈거 즉시 ISR에서 `_ioError = true`를 세팅하고 진행 중인 모든 VFS I/O를 우회(Bypass)하도록 드라이버 레벨의 회피 로직을 구성해야 함.

코어 운영체제(RTOS) 스케줄링, 메모리 버스 대역폭, 하드웨어 예외 처리 관점에서 파이프라인 전체를 심층 재점검함. 실제 공정 환경 적용 시 장비 다운(Crash)이나 영구 손상을 유발할 수 있는 5가지 심층 결함을 추가 도출함.

### 1. 하드웨어 예외 및 메모리 경합 결함 (Hardware Exception & Contention)

* **[결함 1] 팩킹 구조체(Packed Struct) 내 FPU 비정렬 접근 패닉**
* **원인:** `T215_Type_250.hpp`의 웹소켓 전송 패킷(`ST_PktWaveformAudio_t` 등)에 `__attribute__((packed))`가 선언됨. 헤더 크기에 따라 내부 `float` 배열의 메모리 시작 주소가 4바이트 정렬(Alignment)에서 어긋남.
* **영향:** ESP32-S3의 하드웨어 부동소수점 유닛(FPU)이나 SIMD가 비정렬된 `float` 데이터에 접근하여 복사 연산을 수행하는 순간, `LoadStoreAlignment` 예외를 뿜고 시스템이 즉시 강제 재부팅됨.
* **해결책:** 패킷 구조체에서 `packed` 속성을 걷어내거나, 선행 구조체인 `ST_WsHeader_t`의 크기가 무조건 4바이트의 배수가 되도록 내부에 더미(Dummy) 패딩을 명시적으로 강제해야 함.


* **[결함 2] PSRAM 기반 락프리 링버퍼의 코어 간 캐시 동기화 붕괴**
* **원인:** `T216_RingBuf`는 `std::atomic_thread_fence`를 사용함. 버퍼가 내부 SRAM에 있을 때는 정상 동작함. 외부 확장 메모리(PSRAM)에 할당된 상태에서 코어 0(수집)과 코어 1(처리)이 데이터를 주고받을 때, ESP32-S3 아키텍처 특성상 소프트웨어 메모리 펜스만으로는 L1 캐시가 물리 메모리로 즉각 플러시(Flush)되지 않음.
* **영향:** 링버퍼 포인터는 넘어갔으나 데이터는 구형(Stale Data) 상태로 남아, 특징량 추출 시 파형이 심하게 찢어지거나 왜곡된 쓰레기 값이 연산됨.
* **해결책:** 링버퍼 내부 `enqueue`의 데이터 복사 직후와 `dequeue`의 데이터 읽기 직전에 페이로드 주소를 타겟으로 `esp_cache_msync` 함수를 호출하여 하드웨어 캐시 일관성을 강제 보장해야 함.


* **[결함 3] 타임머신 스냅샷 덤프 시 대역폭 경합 (PSRAM vs SDIO)**
* **원인:** 고장 감지 트리거 발생 시 `T260_Storage`가 PSRAM에 적재된 3초 분량의 대용량 프리트리거 데이터를 SD 카드(SD_MMC)로 일괄 덤프함.
* **영향:** SD 카드 쓰기 작업이 SPI/SDIO 버스를 독점하는 동안 대역폭 경합이 발생함. 백그라운드에서 상시 구동되어야 할 I2S 마이크 수집 DMA가 메모리에 접근하지 못해 치명적인 오디오 유실(Drop)이 발생하고, 태스크 지연으로 WDT 타임아웃 패닉이 유발됨.
* **해결책:** 덤프 로직을 일괄 처리 대신 4KB 단위 청크(Chunk)로 분할함. 반복문 사이에 `vTaskDelay(1)`을 삽입하여 버스 점유율을 시스템에 반환(Yield)하는 스로틀링(Throttling) 구조로 재설계함.



### 2. 제어 흐름 및 스토리지 수명 결함 (Flow Control & Wear-out)

* **[결함 4] 지연 쓰기(Lazy Write) 주기에 따른 플래시(LittleFS) 마모**
* **원인:** `T220_CfgMgr`에 `updateConfigLazy` 기능이 존재함. 노이즈 프로필 자동 학습이나 캘리브레이션 보정이 반복되는 환경에서, `T290_FsmMgr`의 메인 루프가 상태 변화마다 무분별하게 지연 쓰기 타이머를 갱신함.
* **영향:** 강력한 쿨다운(Cooldown) 보호 장치가 없으면 공정 노이즈가 출렁일 때마다 내부 플래시 쓰기가 빈번히 발생함. 수개월 내에 플래시 메모리 셀 수명이 소진되어 장비가 영구적인 벽돌 상태가 됨.
* **해결책:** 지연 쓰기 검사(`checkLazyWrite`) 로직에 최소 플러시 유예 기간(예: 변경 발생 후 최소 1시간 대기 또는 시스템 재부팅/유휴 상태 전이 시 일괄 저장)을 강제하는 하드 리미트를 설정함.
ㅣ

* **[결함 5] 배터리 모드 딥슬립 무한 웨이크업(Wake-Loop) 버그**
* **원인:** 간헐 구동 시나리오 대응을 위해 `T230`에서 BMI270의 Any-Motion 하드웨어 인터럽트를 세팅하고 딥슬립에 진입함.
* **영향:** 진입 직전에 센서의 인터럽트 상태 레지스터(Status Register)를 읽어 기존에 발동된 래치(Latch)를 클리어하지 않으면, 이미 활성화되어 있는 핀 상태로 인해 시스템이 딥슬립 진입 즉시 다시 깨어나는 무한 루프에 빠져 배터리가 순식간에 방전됨.
* **해결책:** `T290_FsmMgr`에서 `esp_deep_sleep_start()`를 호출하기 바로 직전에, `_bmi.getInterruptStatus()`를 강제 실행하여 남아있는 하드웨어 인터럽트 찌꺼기를 완전히 비워내는 클리어 루틴을 삽입함.
