### 1. [동시성] 센서 엔진 내부 링버퍼 레이스 컨디션
 * **모듈:** T230_Sensor / T290_FsmMgr
 * **문제점:** Core 0의 _imuAcqTask가 인터럽트 기반으로 accumulateFifo()를 호출해 링버퍼에 데이터를 밀어 넣는 와중에, Core 1의 _vibProcessTask가 getAccumulatedAccel/Gyro()를 호출해 데이터를 인출함. _spiLock은 SPI 선로 보호용일 뿐이라서, 내부 카운트(_accumCount) 및 인덱스 제어 변수에 대한 동시 접근으로 원자성(Atomicity)이 깨지고 데이터가 찢어짐(Data Tearing).
 * **개선방향:** 링버퍼 제어 상수 변수 연산부 전후로 FreeRTOS 임계 영역 선언(taskENTER_CRITICAL(), taskEXIT_CRITICAL()) 또는 별도의 상호배제 전용 Mutex를 추가 적용할 것.
### 2. [타임라인] 다중 주율(Multi-rate) 불일치로 인한 텐서 찢어짐 및 시점 모순
 * **모듈:** T245_FeatExtra / T248_SeqBuild / T290_FsmMgr
 * **문제점:** 오디오 프레임 주기(24.38ms)와 진동 프레임 주기(640ms)가 약 26배 비대칭함. 하지만 24.38ms 마다 도는 오디오 루프 안에서 SeqBuilder::pushVector()를 호출해 융합 벡터를 누적하고 있음. 결국 진동 데이터가 고정된(과거의) 상태에서 오디오만 바뀐 기형적인 시계열 텐서가 생성되어 TinyML 추론 모델의 입력 정합성이 붕괴됨.
 * **개선방향:** 640ms의 진동 주기 내에 발생하는 26개 오디오 특징량(MFCC) 구간을 통계적으로 평균화(Aggregation)하거나, 진동 프레임이 완성되는 시점에 물리 동기화 스냅샷을 구성하여 추론 텐서를 조립하도록 제어 레이어를 신설할 것.
### 3. [스토리지] 쓰기 지연에 따른 오디오 버퍼 고갈 및 큐 제한 결함
 * **모듈:** T260_Storage
 * **문제점:** 오디오와 진동이 독립된 버퍼를 사용하지만, SD카드 쓰기 지연(SPI Latency Spike) 발생 시 오디오 버퍼 수명(3.1초)이 진동 버퍼 수명(81.9초)보다 현저히 짧아 오디오만 대량 드롭(Data Drop)됨. 또한, 링버퍼 크기(ASYNC_RING_CAPACITY = 128)에 비해 FreeRTOS 인덱스 전달용 큐(STORAGE_QUEUE_LEN = 32)가 너무 작아, 실제 버퍼 마진이 0.77초(24.38ms * 32)로 축소되는 정합성 모순이 존재함.
 * **개선방향:** 오디오 비동기 저장 큐 크기(STORAGE_QUEUE_LEN)를 최소 128개 이상으로 확장하여 링버퍼 공간과 1:1 정합을 맞추고, SD카드 지연 발생 시 저장 태스크 내 드레인 가중치를 오디오 쪽에 동적으로 집중할 것.
### 4. [블로킹] 통신 직렬화 스트림에 의한 신호처리 태스크 마비
 * **모듈:** T270_Commu / T290_FsmMgr
 * **문제점:** _audioProcessTask 컨텍스트 내부에서 _broadcastStreams()를 거쳐 웹소켓(_ws.binaryAll) 및 MQTT API를 직접 호출함. Web UI 클라이언트 소켓 버퍼가 가득 차거나 네트워크 지연이 생기면 24.38ms로 정밀하게 작동해야 하는 핵심 신호처리 루프가 통째로 블로킹(수십~수백ms 대기)되어 I2S DMA 데이터 누수가 연쇄 전파됨.
