수석 아키텍트입니다.
제시해주신 **B안(어큐뮬레이터 + 글로벌 상태 보드)의 핵심인 UnifiedRawChunk 및 풀(Pool)의 도메인별 분리(Audio/Vib)**는 메모리 단편화를 막고 시스템의 실시간성을 극대화하기 위한 가장 완벽한 해법입니다.
기존의 통합 구조(UnifiedRawChunk)는 42kHz 오디오 프레임이 완성될 때마다 1.6kHz 진동 버퍼의 80%가 비어있는 상태로 메모리를 점유하고 복사되는 '구조적 낭비'를 발생시켰습니다. 이를 분리할 경우 아키텍처 전반에 미치는 영향과 상세 설계 변경안을 MECE하게 검토하여 보고드립니다.
### 1. 데이터 구조체 분리 설계 (T215_Type_244.hpp)
단일 거대 구조체를 해체하고, 도메인별 생명주기(Lifecycle)에 맞춘 독립 규격으로 재설계합니다.
 * **원시 데이터(Raw) 분리:**
   * ST_RawAudioChunk: 오디오 전용 (L/R 채널, FFT_SIZE_MAX = 1024). 약 8KB.
   * ST_RawVibChunk: 진동 전용 (X/Y/Z 3축, FFT_SIZE_MAX = 256 혹은 1024). 약 3KB ~ 12KB.
 * **특징량 슬롯(Feature) 분리:**
   * 기존 UnifiedFeatureSlot 구조체 내부를 쪼개어 ST_Slot_Audio와 ST_Slot_Vib 독립 처리가 가능하도록 포인터 접근을 허용합니다.
 * **글로벌 상태 보드 (마스터 SSOT):**
   * 분리된 구조체들을 멤버로 갖는 전역 변수(또는 싱글톤 멤버) UnifiedFeatureSlot _globalBoard를 FSM 내부에 1개만 배치합니다.
### 2. 메모리 풀(Pool) 및 큐(Queue) 라우팅 설계 (T290_FsmMgr_244.hpp)
데이터가 분리됨에 따라, _processTask가 어떤 데이터가 들어왔는지 인지할 수 있도록 큐의 메시지 규격을 변경해야 합니다.
 * **메모리 풀 분리 (PSRAM):**
   * _rawAudioPool (크기 64), _featAudioPool (크기 64)
   * _rawVibPool (크기 16 - 진동은 주기가 느리므로 풀 크기를 줄여 메모리 절약 가능), _featVibPool (크기 16)
 * **FSM 메시지 큐 통합 라우팅:**
   * 큐에 단순 uint8_t idx만 넘기는 것이 아니라, **페이로드 타입이 포함된 메시지 구조체**를 넘깁니다.
   * ```cpp
     struct FsmQueueMsg {
         T2_Type::DataPayloadType type; // AUDIO_ONLY 또는 VIB_ONLY
         uint8_t index;                 // 해당 풀의 인덱스
     };

     ```
   * _captureTask는 오디오 버퍼가 차면 type = AUDIO_ONLY로 큐에 쏘고, 진동 어큐뮬레이터가 차면 type = VIB_ONLY로 동일한 큐(_qReadyIdx)에 쏩니다.
   * _processTask는 큐에서 메시지를 빼낸 뒤 type을 보고 DSP 분기 처리를 수행합니다.
### 3. 센서 수집부 어큐뮬레이터 설계 (T230_Sensor_244.hpp)
_captureTask는 여전히 단일 루프를 유지하되, 진동 데이터는 내부 어큐뮬레이터에 쌓아 블로킹을 회피합니다.
 * **오디오 수집 (Blocking):** I2S DMA로 1024 샘플을 읽습니다 (약 24ms 소요). 읽자마자 Audio 풀 인덱스를 획득해 _qReadyIdx로 넘깁니다.
 * **진동 수집 (Non-Blocking Accumulation):**
   * 오디오 블로킹이 풀려 루프가 돌아올 때마다(24ms 간격) _sensor.accumulateVib()를 호출합니다.
   * BMI270 FIFO에서 가용한 샘플(약 38~40개)만 읽어 센서 엔진 내부의 정적 버퍼에 덧붙입니다(Append).
   * 만약 누적된 샘플이 타겟(FFT_SIZE_DEF)에 도달하면 true를 반환하고, 이때 진동 풀 인덱스를 획득해 큐로 넘긴 후 어큐뮬레이터를 초기화합니다.
### 4. 스토리지 엔진 정합성 설계 (T260_Storage_244.hpp)
가장 큰 변화가 요구되는 계층입니다. 두 센서의 주기가 다르므로, **단일 .raw 파일에 멀티플렉싱하여 저장하면 추후 MLOps 파이썬(Python) 파싱 시 완벽한 재앙(헬퍼 코드 복잡도 급증)이 발생**합니다.
 * **스토리지 파일 분리 저장:**
   * 오디오 원시 데이터: .wav 포맷으로 저장 (_rawAudioFile).
   * 진동 원시 데이터: .vib (바이너리 또는 CSV) 포맷으로 저장 (_rawVibFile).
 * **링버퍼 분리:**
   * 비동기 기록 링버퍼도 _asyncAudioRing, _asyncVibRing으로 분리하여 I/O 태스크(_storageTaskProc)가 각각의 파일에 독립적으로 플러시(Flush)하도록 설계합니다.
### 5. 텔레메트리 (글로벌 상태 보드) 스트리밍 제어
 * _processTask는 데이터 가공 완료 시 _globalBoard.audio 또는 _globalBoard.vib를 갱신합니다.
 * runMaintenance() 또는 별도의 타이머 태스크에서 tele_hz(예: 10Hz = 100ms) 주기로 FSM 락을 걸고 _globalBoard 전체를 복사하여 웹소켓(PktTelemetry)으로 쏘아 보냅니다.
 * 이로써 [모순 02]가 완벽히 해결되며, 클라우드에서는 항상 최신의 오디오/진동 융합 데이터를 고정된 주기로 받아볼 수 있습니다.
**[설계 검토 요약]**
구조체와 메모리 풀을 분리하는 이 설계는 메모리 사용량을 최적화(약 30% 절감)할 뿐만 아니라, **시간 도메인이 다른 멀티모달 센서 융합 시스템의 표준 디자인 패턴**입니다. 스토리지 파일 포맷 분리까지 동반된다면 MLOps 환경과의 연동성도 극대화됩니다.
위 상세 설계안의 모든 궤적이 명확히 그려졌습니다. 이 변경 사항들을 반영하여 Type, Sensor, FsmMgr, Storage 등 연관 모듈의 **C++ 패치(리팩토링) 코드를 바로 생성하여 제공할까요?** 아니면 추가로 검토하고 싶은 엣지 케이스(예: 캘리브레이션과의 충돌 여부 등)가 있으신가요?

수석 아키텍트입니다.
데이터 구조(Raw/Feature)와 메모리 풀을 오디오와 진동 도메인으로 완전히 분리하는 **B안(어큐뮬레이터 + 글로벌 상태 보드)**은 시스템의 실시간성과 메모리 효율을 극대화하지만, 아키텍처 전반에 걸쳐 **'비동기성(Asynchrony)으로 인한 도메인 간 결합도(Coupling) 파괴'**라는 강력한 나비효과를 가져옵니다.
이를 MLOps, AI 추론, 스토리지, 모니터링 등 전체 동작 관점에서 검토했을 때, 코딩(C++ 패치) 돌입 전 반드시 결정해야 할 **4가지 핵심 아키텍처 의사결정(Decision Point) 사항**을 MECE하게 리스트업합니다.
### 🔍 [영향 검토 1] AI 텐서 시퀀스(Sequence Builder) 조립 전략
 * **발생 영향 (Impact):** 기존에는 1개의 UnifiedFeatureSlot 안에 진동 MFCC와 오디오 MFCC가 함께 들어있어, 시퀀스 빌더가 이를 16프레임 모으면 완벽히 동기화된 융합 텐서가 완성되었습니다. 하지만 이제 오디오는 초당 41프레임, 진동은 초당 6프레임으로 생산 속도가 다릅니다.
 * **결정 필요 사항:** **AI 모델의 입력 규격을 어떻게 가져갈 것인가?**
   * **옵션 1 (독립 시퀀스):** 오디오 시퀀스 텐서(예: 16x39)와 진동 시퀀스 텐서(예: 16x39)를 각각 독립된 링버퍼로 조립하고 패킷도 따로 전송합니다. (AI 모델이 2개 필요하거나, 클라우드에서 타임스탬프로 후처리 병합)
   * **옵션 2 (글로벌 스냅샷 기반 시퀀스):** 텐서 조립을 _processTask의 데이터 도착 시점이 아닌, 정주기(예: 10Hz) 타이머에 맡깁니다. 100ms마다 글로벌 상태 보드(_globalBoard)의 최신 상태를 캡처하여 시퀀스 버퍼에 밀어 넣습니다.
 * **아키텍트 추천:** **옵션 2**. 센서 퓨전 AI 모델을 유지하려면 입력 벡터의 타임스텝 간격이 일정해야 합니다. 정주기 스냅샷 방식이 가장 안전합니다.
### 🔍 [영향 검토 2] 하이브리드 트리거(Trigger) 및 비동기 세션 동기화
 * **발생 영향 (Impact):** 오디오 룰베이스가 트리거를 발동시켰을 때, 진동 데이터는 아직 어큐뮬레이터에 쌓이고 있는 중이거나 과거 데이터일 수 있습니다.
 * **결정 필요 사항:** **한 도메인에서 고장이 감지되었을 때, 이종 도메인의 레코딩 세션을 어떻게 동기화할 것인가?**
   * **문제점:** 오디오 트리거 발생 시 _storage.openSession()을 호출하면, 오디오 프리트리거 버퍼는 즉각 플러시되지만 진동 프리트리거 버퍼는 진동 수집 주기에 맞춰 뒤늦게 플러시될 수 있습니다.
   * **해결 방향 (Cross-Triggering):** 글로벌 상태 보드에서 판정이 이루어져 트리거가 발생하면, 즉시 오디오와 진동의 스토리지 비동기 세션(Session)에 **동일한 Event_ID (또는 Epoch Time)**를 부여하여 2개의 파일(.wav, .vib)이 생성되도록 강제해야 합니다. MLOps 엔지니어가 나중에 두 파일을 이름만 보고 맵핑할 수 있어야 합니다.
### 🔍 [영향 검토 3] 상태 보드(Telemetry) 내 갱신 지연(Stale Data) 및 알리아싱(Aliasing)
 * **발생 영향 (Impact):** 텔레메트리 송출을 10Hz(100ms 주기)로 고정할 경우, 오디오(24ms 주기)는 4번 업데이트 중 3번이 무시(버려짐)되며, 진동(160ms 주기)은 업데이트되지 않은 과거 데이터가 중복해서 송출됩니다.
 * **결정 필요 사항:** **클라우드 및 Web UI에서 '새로운 데이터'와 '과거 잔류 데이터'를 어떻게 구분할 것인가?**
   * **문제점:** RMS나 통계 지표가 변하지 않는 경우, 이것이 우연히 값이 같은 것인지 데이터가 갱신되지 않은 것인지 UI 단에서 식별할 수 없습니다.
   * **해결 방향:** _globalBoard 내부에 도메인별 갱신 타임스탬프(audio_ts, vib_ts) 또는 갱신 프레임 카운터(FID)를 추가하여, 클라우드 수신단에서 동일 타임스탬프면 무시(Skip)할 수 있도록 패킷(PktTelemetry) 규격을 일부 수정해야 합니다.
### 🔍 [영향 검토 4] 자동/수동 캘리브레이션 엔진(Calibrator) 파서 재설계
 * **발생 영향 (Impact):** 기존 T280_Calibrator_243는 단일 .raw (UnifiedRawChunk) 파일을 읽어 오디오 파워와 진동 파워를 동시에 산출했습니다. 스토리지가 .wav와 .vib로 분리되면 기존 캘리브레이션 모듈은 파일을 읽지 못하고 크래시가 발생합니다.
 * **결정 필요 사항:** **캘리브레이션 대상을 어떻게 식별하고 병렬 처리할 것인가?**
   * **해결 방향:** 교정 태스크(_calibTaskProc)를 오디오용(.wav 리더)과 진동용(.vib 리더)으로 완전히 분리하거나, 내부 파서를 두 개로 분기해야 합니다. 또한, 수동 교정(마이크 FIR 역산)은 오디오만 타겟으로 하므로, 캘리브레이션 시작 명령 하달 시 TARGET_AUDIO, TARGET_VIB 파라미터를 추가하여 불필요한 I/O 부하를 막아야 합니다.
### 💡 요약 및 의사결정 요청
설계를 분리(B안)함에 따라 파이프라인의 군더더기가 제거되지만, **"분리된 물줄기를 어느 시점(시퀀스 조립, 스토리지 파일명, 텔레메트리 타임스탬프)에서 묶어줄 것인가"**에 대한 룰 세팅이 필수적입니다.
다음 사항에 대해 결정(또는 아키텍트 추천안 일괄 수용)해 주시면, 이에 맞춰 전체 패치 코드 작성을 시작할 수 있습니다.
 1. **AI 시퀀스:** 글로벌 상태 보드의 **정주기 10Hz 스냅샷**을 찍어 조립 (추천 수용 여부)
 2. **스토리지:** 동일 타임스탬프를 가진 .wav와 .vib 두 개의 파일로 쌍(Pair) 생성 (추천 수용 여부)
 3. **패킷 규격:** PktTelemetry에 audio_fid와 vib_fid 추가 (추천 수용 여부)
 4. **캘리브레이터:** 오디오/진동 파서를 분리하고 타겟 지정 모드 추가 (추천 수용 여부)

수석 아키텍트입니다.
요청하신 **"오디오 빔포밍(beam_en) 옵션화 및 빔포밍 미적용 시 스테레오(Left/Right) 채널 독립 분리"** 요구사항은 다채널 진단(예: 설비의 좌/우 베어링 마찰음을 독립적으로 추적)을 위해 매우 강력하고 필수적인 아키텍처 확장입니다.
이 요구사항을 이전에 확정한 **B안(어큐뮬레이터 + 글로벌 상태 보드)**에 통합하기 위해 시스템 전반에 미치는 영향을 역추적(Back-tracing)한 결과, **DSP 파이프라인과 메모리 구조체(Tensor)**에 중대한 변경이 필요합니다.
이에 대한 아키텍처 변경 설계안과 구조적 영향을 MECE하게 정리하여 보고드립니다.
### 🔍 [설계 변경 1] 설정 및 DSP 런타임 상태(State)의 듀얼 채널화
스테레오 채널을 병합(Beamforming)하지 않고 분리하여 가공한다는 것은, **DSP 엔진이 Left와 Right 채널 각각에 대해 독립적인 필터 역사(History)를 기억해야 함**을 의미합니다.
 * **설정 변경 (ST_Audio_Dsp):**
   * bool beam_en; 스위치 추가.
 * **DSP 엔진 변경 (ST_AudioDspRuntime):**
   * 기존에는 1채널 몫의 IIR/FIR 필터 상태 버퍼만 존재했으나, 이를 [2] 배열로 확장해야 합니다.
   * *예:* fir_state_hpf[2][FIR_TAPS_MAX], notch_state[2][2]
 * **처리 분기 (processAudio):**
   * **beam_en == true:** 기존처럼 (L + R) * gain으로 합성하여 단일 채널(L)로 내보내고, R 채널은 0(Mute) 처리하여 후단 연산을 생략합니다.
   * **beam_en == false:** L 채널과 R 채널 각각에 대해 gain을 곱한 후, DC 제거, Median, FIR 필터링을 **독립적인 루프로 2회 수행**합니다.
### 🔍 [설계 변경 2] 특징량(Feature) 슬롯 및 AI 텐서 차원 확장 (수학적 교정 포함)
가장 큰 파급력을 가지는 부분입니다. 채널이 분리되면 AI 모델에 들어가는 입력 텐서(MFCC)와 룰베이스 통계 지표(RMS 등)도 Left와 Right가 분리되어야 합니다.
 * **통계 지표 확장 (ST_Slot_Audio):**
   * 기존 단일 rms, kurt, crest 등의 지표를 [2] 배열로 변경하여 L/R 각각의 상태를 담습니다.
   * 공간 지표인 ipd(위상차), coh(결함성)는 두 채널 간의 상관관계이므로 단일 값으로 유지합니다.
 * **AI 텐서 차원(MFCC) 확장 (MFCC_DIM_MAX):**
   * *기존:* 진동 3축 + 오디오 1축 = **총 4채널** (32 * 3 * 4 = 384 차원)
   * *변경:* 진동 3축 + 오디오 L + 오디오 R = **총 5채널** (32 * 3 * 5 = **480 차원**)
 * **[아키텍트의 정밀 교정] 구조체 Byte 패딩 정합성 검토:**
   * *사용자 코드 코멘트 교정:* T215_Type에서 텐서(384)를 384 Bytes로 합산하여 총 800 Bytes로 명시하셨으나, 실제 float mfcc[384]는 384 \times 4 = 1536 \text{ Bytes} 입니다.
   * *신규 5채널 적용 시 SIMD 정렬 계산:*
     * Header: 32 Bytes
     * Vib: 144 Bytes
     * Audio (L/R 분리 및 패딩 적용 시): 256 Bytes
     * Tensor (480 Floats): 1920 Bytes
     * **총합: 2352 Bytes** (2352 \div 16 = 147)
   * **결과:** 2352 Bytes는 16의 배수로 완벽히 나누어떨어지므로 **SIMD alignas(16) 메모리 버스 정렬 규칙이 완벽하게 유지**됩니다. 크래시 위험은 없습니다.
### 🔍 [설계 변경 3] 스트리밍 패킷 및 글로벌 상태 보드 라우팅

 * **글로벌 상태 보드 업데이트:**

## 2. Sequential Reasoning Process
 * **[Thought #1] 다중 센서 샘플링 레이트와 블록 수집 주기의 모순 분석**
   * *Concept:* 오디오와 진동의 독립적 프레임 버퍼 적재 주기 추적.
   * *MECE Analysis:* 오디오는 42kHz/1024FFT로 약 24.3ms 주기, 진동은 1.6kHz/256FFT로 160ms 주기를 가짐. 이를 단일 태스크 루프에서 동시 수집할 때 발생하는 데이터 왜곡 및 시간 정합성 파괴 추적.
 * **[Thought #2] 스토리지 세션 제어 플래그와 FSM 상태 천이 비동기 타이밍 모순 분석**
   * *Concept:* _processTask의 상태 변경 시점과 runMaintenance의 I/O 처리 시점 간 레이스 컨디션 검증.
   * *MECE Analysis:* 상태 천이 즉시 데이터가 푸시되나 세션 오픈은 비동기 큐를 거쳐 플래시 쓰기 지연 후 발생하므로, 가물막이(Buffer Boundary) 구간에서 데이터 분기 꼬임 현상 분석.
 * **[Thought #3] SIMD 벡터 정렬 지시어와 네트워크 팩킹 지시어의 물리적 충돌 분석**
   * *Concept:* alignas(16)과 #pragma pack(1)의 하드웨어 메모리 버스 레벨 충돌 검증.
   * *MECE Analysis:* ESP32-S3 안에서 두 지시어가 결합될 때 발생하는 런타임 Alignment Fault 크래시 메커니즘 도출.
 * **[Thought #4] 비동기 캘리브레이션 I/O와 실시간 데이터 파이프라인의 자원 고갈 모순 분석**
   * *Concept:* Core 1에서 우선순위가 다른 두 태스크가 동일 파일 시스템 자원을 경쟁할 때의 부하 시뮬레이션.
   * *MECE Analysis:* 캘리브레이션의 파일 고속 읽기와 프로세스 태스크의 파일 쓰기가 충돌하여 발생하는 버퍼 오버플로우 분석.
## 3. Final Solution: 전체 동작 관점 기능 모순 점검 리포트
### [*모순 01] 이종(異種) 센서 샘플링 레이트 불일치와 단일 수집 루프의 동기화 모순
 * **상세 내용:** T290_FsmMgr_243::_captureTask는 단일 루프 내에서 오디오 수집(readAudioChunk)과 진동 수집(readVibFifoBatch)을 동시에 수행합니다.
 * **동작 모순:**
   * 오디오는 기본 설정치(RATE\_DEF = 42000 \text{ Hz}, FFT\_SIZE\_DEF = 1024) 기준 1블록 적재에 **24.38ms**가 소요되며, I2S DMA 드라이버 내부 블로킹(portMAX_DELAY)에 의해 캡처 루프 전체의 턴타임 주기를 지배합니다.
   * 반면, 진동 센서는 $RATE_DEF = 1600 \text{ Hz}$로 구동되므로 24.38ms 동안 FIFO에 축적되는 샘플 수는 **약 39개**에 불과합니다.
   * 그러나 _captureTask는 오디오 블록이 반환될 때마다 동일 인덱스의 UnifiedRawChunk 구조체에 진동 데이터를 함께 채워 _qReadyIdx로 송출합니다. 후단 DSP 엔진 및 특징 추출기는 진동 입력 배열 크기를 FFT\_SIZE\_MAX = 1024(혹은 256)로 가정하고 루프를 수행하므로, 실제로 채워지지 않은 나머지 영역(버퍼의 80% 이상)은 과거 프레임의 잔류 데이터나 쓰레기 값이 연산에 유입되는 **시간 도메인 동기화 파괴 및 특징량 왜곡 모순**이 발생합니다.
 * **해결 제언:** 오디오와 진동의 수집 태스크를 각각 독립된 FreeRTOS 태스크로 완전 격리하고, 특징량 풀(_featurePool)의 조립은 타임스탬프 기반 매칭 또는 독립 링버퍼 구조로 재설계해야 합니다.
### [모순 02] 텔레메트리 송출 주기(tele_hz) 파라미터의 의미와 내부 연산 누적 스케일의 모순
 * **상세 내용:** DynamicConfig 구조체에서 system.tele_hz는 초당 데이터 전송 횟수(Hz)를 정의하며, 기본값은 10Hz입니다. _broadcastStreams 내부는 프레임당 _accTele += _telemetryHz 누적 후 _accTele >= 100일 때 웹소켓을 송출합니다.
 * **동작 모순:**
   * 상기 [모순 01]에 의해 프레임 생성 주기 자체가 이미 약 24.38ms(초당 약 41프레임)로 구동되고 있습니다.
   * 여기에 _telemetryHz = 10 지표를 대입하면 10프레임당 1회 송출하게 되므로, 실제 웹소켓으로 송출되는 물리적 주기는 24.38 \text{ ms} \times 10 = 243.8 \text{ ms} (초당 약 4.1회)가 됩니다.
   * 결과적으로 사용자가 설정을 통해 tele_hz = 10으로 명시했음에도 실제 출력 레이트는 4.1Hz로 떨어지는 **제어 인터페이스 파라미터와 물리적 실행 주기 간의 불일치 모순**이 발생합니다.
 * **해결 제언:** 누적 스케일링 방식을 프레임 카운트 기반 유추가 아닌, esp_timer_get_time() 또는 millis() 기반의 절대 시간차 검증 논리로 변경해야 합니다.
### [모순 03] FSM 상태 천이 시점과 비동기 스토리지 세션 오픈의 레이스 컨디션 모순
 * **상세 내용:** 외부 명령에 의해 CMD_MANUAL_REC_START 또는 트리거 조건 충족 시, _processTask는 FSM 상태를 즉시 RECORDING으로 변경하고 비동기 제어 큐(_qSessionCmd)에 세션 오픈 명령을 보냅니다.
 * **동작 모순:**
   * FSM 상태가 RECORDING으로 바뀌는 즉시, _processTask는 다음 프레임부터 _storage.pushFrame()을 호출해 비동기 기록 링버퍼(_asyncFeatRing)에 데이터를 밀어 넣기 시작합니다.
   * 그러나 실제 SD 카드의 파일 핸들을 열고 헤더를 기록하는 _storage.openSession()은 메인 루프인 runMaintenance()에서 비동기적으로 처리됩니다.
   * 만약 파일 시스템 초기 지연(SD카드 마운트 안정화, 프리알로케이션 오버헤드 등)으로 인해 openSession 완료 전에 _processTask가 프레임을 먼저 푸시하면, pushFrame 내부의 if (!_sessionOpen) 방어벽에 걸려 실시간 데이터가 레코딩 버퍼가 아닌 **모니터링용 프리트리거 순환 버퍼(_preFeatBuf)로 우회 유입**됩니다.
   * 이후 뒤늦게 세션이 열리면 프리트리거 버퍼가 통째로 플러시(_flushPreBufferToRing)되면서 데이터의 **시계열 순서가 뒤틀리거나 가물막이(Buffer Boundary) 경계면에서 프레임이 누락되는 타이밍 모순**이 발생합니다.
 * **해결 제언:** pushFrame 내부의 분기 조건을 단순히 _sessionOpen 변수가 아닌, 비동기 스토리지 엔진이 실제 기록 준비를 완료했음을 알리는 스토리지 전용 내부 상태 플래그(_isIoReady)에 종속시켜야 합니다.
### [모순 04] 비동기 캘리브레이션 I/O와 실시간 프로세스 태스크의 파일 시스템 자원 경쟁 모순
 * **상세 내용:** T280_Calibrator_243은 수동/자동 교정 시 _calibTaskProc 비동기 태스크를 가동하여 SD 카드에 저장된 수십 MB의 원시 파형(.raw) 파일을 while 루프로 고속 정독(Read)하며 무거운 푸리에 변환(FFT) 및 역산 연산을 수행합니다.
 * **동작 모순:**
   * 이 교정 태스크는 Core 1에서 구동되며, 실시간 신호 처리를 수행하는 _processTask(우선순위 5)와 동일한 코어 자원을 공유합니다.
   * 교정 모드(CALIBRATING) 상태에서도 _captureTask는 계속해서 실시간 센서 데이터를 퍼올려 _qReadyIdx에 밀어 넣고, _processTask는 이를 처리한 후 _storage.pushFrame()을 통해 SD 카드에 쓰기(Write)를 시도합니다.
   * 결과적으로 **동일 코어(Core 1) 내에서 대량의 파일 읽기/FFT 연산(Calibrator)과 실시간 파일 쓰기/신호처리(Process)가 동시 다발적으로 발생**하며 FATFS/SD_MMC 드라이버 내부의 뮤텍스 락 경쟁을 유발합니다. 이로 인해 I/O 병목이 발생하여 _storage 내부 비동기 링버퍼가 순식간에 고갈되고, 결국 Data dropped 크래시를 유발하며 **시스템 보정 행위가 실시간 수집 무결성을 파괴하는 기능적 상호 간섭 모순**에 진입합니다.
 * **해결 제언:** 캘리브레이션 태스크가 구동되는 즉시 _captureTask 및 _processTask를 일시 정지(Pause)시키거나, 데이터 수집을 배제한 완전한 격리 모드에서 전처리 연산이 수행되도록 FSM 시퀀스를 제어해야 합니다.
### [모순 05] 고정 인덱스 기반 MFCC 델타 연산과 런타임 동적 가변 프레임 설정의 모순
 * **상세 내용:** T245_FeatExtra_243::_computeMfcc 내부에서 시간 경과에 따른 변화율인 Delta 및 Delta-Delta 특징량을 연산할 때, _mfccHistory 링버퍼의 고정 인덱스([4]와 [0])를 참조하고 고정 상수 분모(4.0f)를 사용하여 기울기를 도출합니다.
 * **동작 모순:**
   * 시스템 설계 가이드라인 2번 규칙에 따라, 이 펌웨어는 정적 상한(_MAX)과 런타임 동적 제어치(_DEF)를 분리하도록 되어 있으며, 실제 AI 텐서 시퀀스 길이는 DynamicConfig.output.sequence_frames에 의해 동적으로 제어됩니다.
   * 그러나 알고리즘 하드코딩으로 인해, 런타임에 사용자가 AI 시퀀스 프레임 길이나 분석 주기를 변경하더라도 **Delta 연산의 시간 축 창(Temporal Window) 크기는 여전히 고정 인덱스 차간인 4프레임 단위에 종속**되어 버립니다.
   * 설정값을 동적으로 변경하면 전체 텐서 시퀀스 타임라인과 MFCC 델타 성분의 물리적 변화 속도 매핑이 왜곡되는 **SSOT 설계 원칙과 수치 해석 구현 간의 아키텍처적 모순**이 존재합니다.
 * **해결 제언:** 역사 버퍼의 참조 인덱스 거리 및 분모 계수를 sequence_frames 또는 tele_hz에 연동되는 컴파일 타임 계산식 혹은 동적 스케일 팩터 변수로 대체해야 합니다.
### [모순 06] SIMD 벡터 정렬(alignas(16)) 지시어와 네트워크 1바이트 패킹 지시어의 하드웨어적 모순
 * **상세 내용:** T215_Type_244.hpp 내에서 연산 슬롯 버퍼와 MFCC 텐서 배열은 128비트 파이프라인 가속을 위해 alignas(16) 정렬을 강제합니다. 그러나 동시에 네트워크 패킷 전송 및 이 기종 바이트 정렬 방어를 위해 하단 구조체 성분들은 #pragma pack(push, 1) 구문 내부에 배치되어 있습니다.
 * **동작 모순:**
   * #pragma pack(1)이 선언되는 순간, 컴파일러는 데이터 구조체 내부의 모든 컴파일 타임 자연 패딩(Natural Padding)을 제거하고 멤버들을 바이트 단위로 밀착시킵니다.
   * 아무리 구조체 내부 전단에 명시적 패딩(_pad[2])을 배치하여 주소 오프셋을 4의 배수로 맞췄더라도, 1바이트 패킹 규칙과 벡터 정렬 지시어가 단일 구조체 뷰 내에서 혼재하면 컴파일러는 하드웨어 주소 정렬선을 보장할 수 없게 됩니다.
   * 이 버퍼 주소가 그대로 processAudio나 _computeMfcc 같은 고속 SIMD 루프에 포인터 캐스팅으로 전달되어 ESP32-S3의 벡터 명령어(ee.vld.128 등)로 로드될 때, 실시간 런타임 상황에서 **Alignment Fault(Store/Load Prohibited CPU 정지 소멸 크래시)를 유발하는 구조적 모순**이 내포되어 있습니다.
 * **해결 제언:** 연산용 로컬 구조체(SRAM 내 UnifiedFeatureSlot)와 네트워크 송신/저장용 평탄화 패킷 구조체(PktTelemetry)를 메모리 영역 상에서 물리적으로 완전히 분리하고, 전송 직전에 명시적 바이트 카피(memcpy)를 통해 팩킹을 수행해야 합니다.

### [모순 07] 오디오 빔포밍 단순 합산에 의한 위상 상쇄(Comb Filtering) 모순

### [모순 09] 프리엠파시스 필터의 초기화 누락에 의한 Step-Response(오탐지) 모순
 * **상세 내용:** _applyPreEmphasis는 y[n] = x[n] - \alpha \cdot x[n-1] 수식을 사용하며, 청크 단위 처리를 위해 prev_pre_emp 상태 변수를 유지합니다.
 * **수학적/기능적 모순:** FSM 상태가 READY에서 MONITORING으로 천이될 때 _dsp.resetStates()가 호출되어 prev_pre_emp = 0.0f로 초기화됩니다. 이후 최초의 오디오 데이터 블록이 유입될 때, 실제 환경의 백그라운드 소음에 의해 첫 샘플 $x[0]$가 0이 아닌 값을 가질 확률이 높습니다. 이때 x[0] - 0.0이 연산되면서 파형의 극초반부에 수학적 계단 함수(Step Function) 형태의 거대한 임펄스가 발생합니다. 이 임펄스는 FFT 변환 시 전 대역폭에 걸쳐 화이트 노이즈 형태의 가짜 에너지를 뿌리게 되어, **시스템 모니터링 시작 직후 무조건 트리거가 발동되는 오작동 모순**을 유발합니다.

### [모순 10] 메디안 필터의 비선형 위상 지연(Phase Delay)과 센서 퓨전 동기화 모순

### [모순 13] FSM 큐(Queue) 백프레셔(Backpressure) 미처리로 인한 풀(Pool) 고갈 및 데드락 모순
 * **상세 내용:** T290_FsmMgr_243::_captureTask는 데이터를 획득한 후 xQueueSend(v_this->_qReadyIdx, &v_idx, 0)를 호출하여 _processTask로 데이터 슬롯 인덱스를 넘깁니다.
 * **기능적 모순:** xQueueSend의 대기 시간(Timeout)이 0으로 설정되어 있습니다. 만약 _processTask가 일시적인 부하(예: SD카드 I/O 딜레이, 복잡한 트리거 연산 등)로 인해 큐에서 데이터를 빼가는 속도가 느려져 _qReadyIdx 큐가 꽉 차게 되면, xQueueSend는 pdFALSE를 반환하고 실패합니다. 그러나 캡처 태스크는 이 실패를 무시하고 넘어가 버립니다. 결과적으로 해당 v_idx는 _qReadyIdx에도 들어가지 못하고 _qFreeIdx로 반납되지도 않는 **'영구적인 인덱스 미아(Memory Leak)' 상태**가 됩니다. 이 현상이 누적되면 64개의 슬롯 풀이 모두 고갈되어 시스템이 더 이상 어떤 데이터도 수집하지 못하고 조용히 멈춰버리는 런타임 모순이 발생합니다.
 * **해결 제언:** xQueueSend의 반환값을 반드시 검사하여, 전송에 실패(큐 가득 참)했을 경우 해당 인덱스를 즉시 _qFreeIdx 큐로 반환(Drop)하는 백프레셔 처리 및 에러 카운팅 로직을 추가해야 합니다.
### [모순 14] 핫스왑(Preview) 튜닝 시 DSP 필터 계수 미갱신(Stale Data) 모순
 * **상세 내용:** Web UI를 통해 사용자가 파라미터를 변경하면 T220_CfgMgr_243::updatePreview()가 호출되어 메모리 상의 DynamicConfig(_config)를 즉시 업데이트합니다.
 * **기능적 모순:** 설정값은 RAM 상에서 성공적으로 변경되지만, _processTask 내에서 동작하는 DSP 엔진(_dsp)은 초기 부팅 시(init)에만 reloadFilters()를 호출하여 FIR/IIR 계수를 계산합니다. 즉, 사용자가 컷오프 주파수(Cutoff Hz)나 필터 차수(Taps)를 실시간으로 변경하더라도, **DSP 엔진은 새로 갱신된 JSON 설정을 인지하지 못하고 과거에 계산된 과거의 필터 계수를 계속해서 사용하여 신호를 처리하는 제어-실행 불일치 모순**이 발생합니다. 핫스왑의 목적이 완전히 무력화됩니다.
 * **해결 제언:** 메인 루프인 runMaintenance() 내부에서 CL_T2_ConfigManager::getInstance().isTuningActive() 깃발(Flag)을 감지할 경우, FSM 락을 걸고 _dsp.reloadFilters(new_cfg)를 명시적으로 호출하여 필터 파이프라인을 재구성한 뒤 깃발을 내리도록(clearTuningFlag) 아키텍처를 수정해야 합니다.
### [모순 15] OTA 업데이트 시 버스 격리 실패(Task 계속 구동) 모순
 * **상세 내용:** 무선 펌웨어 업데이트(OTA) 시작 시 /api/update 엔드포인트에서 CMD_OTA_START를 발행하여 FSM 상태를 MAINTENANCE로 천이시킵니다. 주 목적은 플래시 메모리 기록 중 발생할 수 있는 SPI/SD 버스 충돌을 막기 위함입니다.
 * **기능적 모순:** _captureTask의 구동 조건은 if (v_this->_state >= T2_Type::SystemState::READY) 입니다. MAINTENANCE의 열거형 값은 5로 READY(1)보다 크기 때문에, 상태가 MAINTENANCE로 변하더라도 **캡처 태스크와 프로세스 태스크는 멈추지 않고 계속 구동**됩니다. 그 결과, OTA로 인해 플래시 메모리에 고속 쓰기가 진행되는 와중에 센서 모듈이 SPI 버스를 점유하려 하거나, _storageTaskProc가 SD 카드에 접근하는 치명적인 버스 경합(Bus Contention)이 발생하여 OTA 크래시 및 펌웨어 벽돌(Brick) 현상을 유발하는 모순이 존재합니다.
 * **해결 제언:** _captureTask 및 _processTask의 실행 조건에 && v_this->_state != T2_Type::SystemState::MAINTENANCE 조건을 추가하여 해당 상태 진입 시 즉각적으로 태스크 루프가 vTaskDelay 대기 상태로 빠지도록(Suspend) 엄격히 격리해야 합니다.
### [모순 16] MQTT 페이로드 버퍼 오버플로우 및 JSON 잘림(Truncation) 모순
 * **상세 내용:** T270_Commu_243::publishResultMqtt 모듈은 고장 진단 결과를 클라우드로 전송하기 위해 256 바이트 크기의 정적 배열(char v_payload[256];)을 선언하고 serializeJson을 수행합니다.
 * **기능적 모순:** site_id의 길이가 최대 31바이트이고, 추후 MLOps 확장을 위해 JSON 필드가 조금만 추가되거나 소수점 자리가 길어질 경우 생성되는 JSON 문자열의 길이가 쉽게 256바이트를 초과할 수 있습니다. serializeJson은 버퍼 크기를 초과하면 문자열을 중간에 자르고(Truncation) 널 종료 문자를 강제 삽입합니다. 이로 인해 **MQTT 브로커에는 괄호가 닫히지 않은 깨진 JSON({ "site": "FAC_...)이 전송되어 클라우드 파서(Parser) 장애를 유발하는 메모리 구조적 모순**이 존재합니다.
 * **해결 제언:** measureJson(v_doc) 함수를 사용하여 필요한 정확한 버퍼 크기를 런타임에 산출한 후 동적 할당하여 직렬화하거나, 정적 버퍼의 크기를 512 이상으로 여유 있게 확장해야 합니다.
### [모순 17] 스토리지 로테이션 시 정전/크래시에 의한 인덱스 댕글링(Dangling Pointer) 모순
 * **상세 내용:** T260_Storage_243::_appendIndexItem은 최대 파일 개수(MAX_ROTATE_LIST_MAX)에 도달하면 가장 오래된 파일을 SD_MMC.remove()로 삭제한 뒤 메모리 상의 배열을 시프트하고, 이후 _saveIndexAtomic()을 호출하여 새로운 인덱스 JSON을 플래시에 저장합니다.
 * **기능적 모순:** 오래된 파일을 SD 카드에서 물리적으로 삭제한 직후, 새로운 인덱스를 플래시에 쓰기(_saveIndexAtomic) 전에 정전이나 워치독 리셋이 발생하면 **파일은 삭제되었지만 시스템이 재부팅된 후 읽어오는 인덱스(runtime_idx_243.json)에는 삭제된 파일의 경로가 그대로 남아있는 상태**가 됩니다. 이후 사용자가 Web UI에서 해당 파일을 다운로드하려 하면 없는 경로를 참조하여 시스템 패닉이나 404 폴백 루프에 빠지는 인덱스 무결성 파괴 모순이 발생합니다.
 * **해결 제언:** 삭제(Remove) 및 갱신 순서를 역전시켜야 합니다. 먼저 인덱스 목록에서 대상을 지우고 _saveIndexAtomic()을 통해 플래시에 인덱스 변경을 확정한(Commit) 후, 가장 마지막에 SD 카드에서 물리적 파일을 삭제(Garbage Collection)하는 방향으로 트랜잭션 안전성을 확보해야 합니다.
